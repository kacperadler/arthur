# Running Arthur on a VPS

Arthur is one process, `arthur run`, in the folder that holds `arthur.config.ts`, kept running by a systemd user service. The install, from a fresh VPS to that service, is [`setup.md`](setup.md), each step with the command that checks it. This page holds the rest: another machine for jobs, the threat model, daily use and updating.

A line that names a roadmap entry describes what that entry builds; the order is [`spec/roadmap.md`](../spec/roadmap.md).

## Another machine for jobs

A job can run on another machine, such as a Mac for an iOS build (`arthur spawn --machine <name>`, roadmap entries 21 and 22; the `machines` plugin of entry 30 declares and checks them, and with entry 31 places each job on a machine that has the labels its spawn, ticket or project `requires`). Arthur reaches it only over SSH, as `ssh -o BatchMode=yes -o StrictHostKeyChecking=yes -o ConnectTimeout=10 <host>`: never with a password, never accepting a host key it does not know, giving up after 10 seconds on a machine that does not answer. The machine runs the job's worktree, agent and guards through its own `arthur`; Arthur sends it no MCP secret, only the task, the prompt, the commits and the variables a plugin's `prepare` returns, such as a provider's key of the models plugin (`arthur spawn --help`, "On another machine"). `arthur stop`, `steer`, `continue` and `prune` of its jobs run there too. It needs:

1. Node 24, git and OMP, logged in with its own credential (`omp login` there), as in steps 2 and 3 of [`setup.md`](setup.md). With the nvm plugin on, nvm in `~/.nvm` there (or `NVM_DIR` set for a command over SSH) and each Node version the projects' `.nvmrc` name, `nvm install <version>` there: a spawn downloads none (`packages/nvm/docs/nvm.md`).
2. Arthur's core of the same version as here: clone and `npm ci` as in step 4 of [`setup.md`](setup.md), at the same commit, without a config. `arthur version` prints the version; both machines must print the same, or every spawn there is refused naming both. Update it there with every update here.
3. `node`, `omp`, `git` and `arthur` on the `PATH` of a command run over SSH, which reads no profile and returns early from Ubuntu's `~/.bashrc`: put the `PATH` line at the top of `~/.bashrc` there, before its `case $- in` line, not at its end. The `machines` plugin's check runs `node -e` there for the machine's free CPU and memory, and with `keepFree.disk` `df -Pk` for its free disk, which the `resources` plugin reads; a machine where `node -e` fails, or where `git` is not found, is offline.
4. From this host, as Arthur's user: a key the machine accepts (`ssh-copy-id <host>`), and its host key known, accepted once by hand. Then this prints the same version as `arthur version` here, without asking anything:

```sh
ssh -o BatchMode=yes -o StrictHostKeyChecking=yes <host> arthur version
```

5. On Linux, linger there (`sudo loginctl enable-linger "$USER"`), so each job gets its scope as in step 10 of [`setup.md`](setup.md), in a slice limited to the machine's own cores minus one and 70% of its memory; without a user manager (macOS) a job runs bare, and a job's `perJob` memory cap of the `resources` plugin is held by sampling its processes every 10 seconds, its CPU not capped.
6. Here, the machine in the `list` of the `machines` plugin in `arthur.config.ts`, with its name, its `ssh` host, its `home` and its labels (see `arthur machines --help`); a host that resolves to a public address is refused at load. `arthur machines` then checks it at once: `online (<os> <arch>, arthur <version>)`, or `offline: <reason>; fix: <fix>`. `arthur run` checks it again at its start and every `check.everySeconds`.

The machine's `home`, as registered, holds the job records (`<home>/jobs/`), each project's repository (`<home>/repos/<project>.git`, created on first use) and the job worktrees (`<home>/repos/.arthur-worktrees/`).

A machine that stops answering (switched off, off the network) does not lose its jobs: they wait `blocked` here and go on there; back within `core.jobs.offlineGraceMinutes` (default 30) they go on here as there, and past it they end `failed: machine offline` here while their worktree there stays for you. A job that ended there meanwhile brings its end and branch once the machine answers again (see `arthur spawn --help`).

## Threat model

Arthur exposes nothing to the internet: no port, no webhook. Every plugin calls out (Telegram and GitHub are polled) or talks to a local process, and other machines are reached over SSH on a private network (Tailscale). A job on another machine can do there whatever that machine's user can, as below. The risk is not who reaches Arthur, but what Arthur and its jobs can reach.

- Arthur, the coordinator and every job run as your Linux user. A job runs `omp` with `bash` and can do whatever you can but write outside its own places (the sandbox below): read your files, use your SSH keys, push wherever they reach, reach the network. A deploy key per repository limits a push to that repository; an account key reaches every repository of the account.
- A channel is a shell. The coordinator acts on what the allowed Telegram chat sends (`telegram`, entry 47), so whoever holds that account holds the VPS. Turn on Telegram's two-step verification.
- Secrets stay in the env file (`core.envFile`) and in the process that needs them. The env guard (entry 19) refuses a tool call of a job or of the coordinator that names a secrets file; a program a job runs can still read any file you can.
- A job's edits stay in its own worktree: the worktree guard (entry 20) refuses a write into the main checkout, `.arthur/`, another job's worktree, another project's main checkout or its jobs' worktrees, Arthur's install (the clone of step 4 of [`setup.md`](setup.md)), the folder of `arthur.config.ts`, the env file, or your `~/.ssh`, `~/.config/systemd` and Git config, `~/.gitconfig` and `~/.config/git/` (also `$XDG_CONFIG_HOME/git/` when Arthur runs with it set elsewhere). A file your Git config includes from elsewhere (`[include] path = ~/dotfiles/gitconfig`) is not followed: a write there passes, and changes Git's identity and hooks in every checkout as a write to `~/.gitconfig` would. It parses commands, so it keeps honest mistakes apart; it is not a sandbox: a program a job runs that writes on its own (`node -e`, `python3 -c`, `tar -C`) or a path built at run time is held only by the sandbox below. It refuses a `git config` that sets or unsets a value in the config every worktree shares, yours (`--global`) or the system's, also through `-C <main>`, `--file <main>/.git/config`, an abbreviated or a `--no-` option; a read, a worktree's own (`--worktree`) and a file outside these places pass, but not an alias or include written there, which later git calls would run unseen. It judges a git call through an alias its `-c` gives as what the alias runs, and through `GIT_DIR=`, `GIT_WORK_TREE=` or `GIT_COMMON_DIR=` before `git` as through `--git-dir` or `--work-tree`; it refuses one that reads config it does not: a shell alias, an include, `--config-env`, or `GIT_CONFIG*`, `HOME` or `XDG_CONFIG_HOME` set for it. It does not refuse the git commands that rewrite the repository every worktree shares, `git gc`, `prune`, `repack`, `reflog expire` and `maintenance run`, a git command reached through an alias already in your Git config or a `GIT_DIR` exported by an earlier command, nor a ref no worktree has checked out that a job moves or deletes from its own worktree. It refuses pointing a checkout at a branch another worktree holds, after which a plain commit would move it: `switch` or `checkout` with `--ignore-other-worktrees`, `checkout -B` and `switch -C` (which Git before 2.44 lets through) but for the job's own branch, `worktree add --force`, `symbolic-ref` but `HEAD` to the job's own branch, and a write of the worktree's own `.git` file. Git reads a `.git` file (`gitdir: <folder>`) or a `commondir` as a link that makes any folder a checkout of the repository it names, so the guard refuses writing a path named `.git` or `commondir` anywhere (to remove a repository, remove its folder), and a git write whose folder, `--git-dir` (a `.git` file of any name) or `--work-tree` links to a guarded place, read from the files as they are when the call starts, also `git init --separate-git-dir` into one; a worktree `git worktree add` made, whose repository folder names it back, passes. Not seen: such a link made and used in the same call by a program, or under another name (`printf 'gitdir: …' > /tmp/l && git --git-dir=/tmp/l commit`).
- The bound is the sandbox each job's agent runs in (`arthur spawn --help`, "The sandbox"): on Linux 5.13 or later with `python3` (Ubuntu 24.04 has both), the agent and every process it starts write only in the job's worktree and record, the Git folders a commit on its branch writes, the temporary folder, `/dev`, `~/.omp` and the job's folder of each plugin extension, and make no Unix socket but a datagram one (omp's session lock), so neither `systemd-run --user`, a tmux server nor another local daemon runs a command outside it. That datagram socket lets a job write lines into your journal, each stamped with its `arthur-job-<id>.scope`, and nothing beyond. Your home folder, the checkouts, Arthur's install, its config and env file, `~/.ssh`, `~/.gitconfig` and `~/.config/systemd` are read-only to it. Where it cannot be set up (macOS, no `python3`), the job's log says `no sandbox: <why>` and the agent writes wherever you can.
- A program a job runs can write the repository's own Git config, which every worktree shares, and Git runs the programs that config names. So Arthur's own git calls in a main checkout, and in a project's repository on another machine (`repos/<project>.git`, which its jobs' worktrees there share; a spawn's push into it runs none of its hooks either), turn off its hooks and `core.fsmonitor` (`-c` on each), and those that may run another program, a worktree's checkout for a spawn (here or on another machine), `arthur merge` (its merge, and the reset after a failed check), `github.push`, and the push and fetch of a job on another machine, are refused, running nothing, while that config (`.git/config`, the main checkout's `config.worktree`, a file either includes) sets a key outside this set: `core.` `repositoryformatversion`, `filemode`, `bare`, `worktree`, `logallrefupdates`, `ignorecase`, `precomposeunicode`, `symlinks`, `autocrlf`, `eol`, `safecrlf`, `hookspath`, `fsmonitor`, `sparsecheckout`, `sparsecheckoutcone`, `untrackedcache`; `extensions.` `objectformat`, `refstorage`, `worktreeconfig`; `remote.<name>.` `url`, `pushurl`, `fetch`, `tagopt`, `prune`, `mirror`; `branch.<name>.` `remote`, `pushremote`, `merge`, `rebase`, `description`; `submodule.<name>.` `url`, `active`; `lfs.repositoryformatversion` and `lfs.<url>.` `access`, `locksverify`; `user.` `name`, `email`; `pull.` `rebase`, `ff`; `push.` `default`, `autosetupremote`; `fetch.prune`; `maintenance.` `auto`, `strategy`; `index.sparse` (what `git init`, `git clone`, Git LFS, a branch's upstream and Arthur write). The refusal names the file and the key: `<file> sets <key>, which a job can write and which may name a program Arthur's git would run; remove it, or set it in your ~/.gitconfig`. A filter, a merge driver, a credential helper, `core.sshCommand`, `gpg.program` or an alias of your own goes into `~/.gitconfig`, which the worktree guard keeps from a job (`[includeIf "gitdir:<checkout>/"]` for one repository). The check runs just before each such call, so a program a job runs that rewrites the config in that moment can still win the race. A remote's `url` and `pushurl` pass it, so `github.push`, and the push and fetch of a job on another machine (whose URL Git reads first as the name of a remote), run with `GIT_PROTOCOL_FROM_USER=0`: Git takes only the transports it allows always, `http`, `https`, `ssh` and `git`, and refuses the others with `fatal: transport '<name>' not allowed`: a helper a URL names (`<name>::<address>` or `<name>://...`, which would run `git-remote-<name>` from your PATH), `ext::`, and a folder or a `file://` URL, whose hooks a push into it would run. An origin of yours that needs one is allowed in `~/.gitconfig` (`git config --global protocol.file.allow always`, or `protocol.<name>.allow`), which allows it to a URL a job writes too. An `ssh` URL still reaches any host your key opens, this one included.
- On another machine the project's repository there (`repos/<project>.git`) is checked the same way: `arthur remote-job repo` refuses a spawn before its push while that repository's own config sets a key outside the set above (`core.alternateRefsCommand`, which `git receive-pack` runs with its hooks off), and `arthur remote-job prune` keeps a job's worktree there while the config it reads, the shared one or its own `config.worktree`, does (a clean filter, which the `git status` of `git worktree remove` runs). The fetch of a job's branch back, `git upload-pack` there, does not run that repository's `core.alternateRefsCommand`.
- A program a job runs can also write a replacement of a commit (`refs/replace`, which every worktree shares), after which Git reads that commit as another one in every checkout: `git status` in the main checkout shows its files staged, and a merge there finds no shared history. The worktree guard refuses `git replace` in a job unless it lists (bare, `-l`, `--list`). The git calls of the line above, and a spawn's check that its ticket is committed, read past any replacement (`--no-replace-objects`). Not covered: a `git fetch` or `git push` from a job's worktree into `refs/replace` passes the guard, and your own git commands and Arthur's other reads (a plan's ticket, a commit rule's file, a merge's lockfile) still read through a replacement; `git replace -l` lists them, `git replace -d <commit>` removes one.
- A job runs only the `arthur` commands its roles need: inside a job the CLI refuses every command not registered with `inJob: true`, so a job does not merge, spawn, stop, steer, prune, send, move the board, change the schedule or record the owner's word (`arthur help --help` lists the ones it runs). The mark is the job's systemd scope, `arthur-job-<id>.scope` in `/proc/self/cgroup`, which no process of the job leaves while the sandbox above holds: it reaches neither `systemd-run --user` nor a `cgroup.procs` to move itself (AR0354). It counts where the home of the arthur.config.ts the CLI reads holds that job's record: a test's home holds none, so a job's own tests act as that home's coordinator. So does a job that writes a config of its own with a home of its own: its file writes are bound by the sandbox, but not what it asks of YouTrack or GitHub with a token of the env file, which it can read (F1 of AR0354). Where a job runs bare (no user manager), the mark is `ARTHUR_JOB`, which the wrapper sets and a job's shell can clear (`env -u ARTHUR_JOB arthur merge …`): there, as without the sandbox, the refusal keeps a mistaken job from acting as the coordinator, not a steered one.
- Limits: time and money per job (entry 12), one joint CPU and memory limit for all jobs (entry 13), so jobs cannot starve the coordinator, and with the `resources` plugin each job's own CPU and memory (entry 32), so one job cannot take all of it, and a new job only on a machine whose free CPU and memory keep `keepFree` after the job's reservation (entry 34).
- Nothing limits the network, and nothing confines reads.
- Text from outside (an issue, a comment, a message from someone else) that reaches a job can steer it with all of the above. Give each client, or anything you do not screen, its own Linux user with its own Arthur.
- `/stopall` (entry 15) stops every running job without the model.

## Daily use

- State and log: `systemctl --user status arthur`, `journalctl --user -u arthur -f`.
- The coordinator's session: `arthur attach` (entry 23); detach with `Ctrl-b d`.
- Stop: `systemctl --user stop arthur`. Start again: `systemctl --user start arthur`.
- `arthur run` by hand while the service runs is refused, naming the service's pid: one `arthur run` per home folder.
- After a crash the next start takes over `run.pid`, whose pid is dead; after a reboot as well, since the file names the boot it was written in; and when the new start has the crashed one's pid (a restarted container), since the file is not one it took.
- Any other command, `arthur <command>`, runs in `~/arthur` beside the service; `arthur help` lists them.

## Updating

```sh
cd ~/arthur
git pull
npm ci
arthur config check
systemctl --user restart arthur
```

A restart stops every plugin, the coordinator included. Run `arthur jobs` first and restart when none runs. Until it, once a pull or a merge changed Arthur's code, the session plugin's restart guard refuses every new job, `restart due: ...` (`packages/session/docs/session.md`, "The restart guard"). While one is due, `/restart` from the phone does this restart too, after the coordinator's handoff (`arthur restart --help`).
