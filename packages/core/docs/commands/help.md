# arthur help

Usage: `arthur help [<command>]`, `arthur <command> --help`

`arthur help <command>` and `arthur <command> --help` print the command's doc page, the file it registered with. `arthur help`, `arthur --help` and `arthur` alone print the usage line and every command's name, the core's and the enabled plugins'.

Every command runs as `arthur <command> [args]`, on `arthur.config.ts` in the working folder, and exits with the command's own code. `--project <name>`, anywhere on the line, tells the command which project to act on instead of the main one; the command gets every other argument as written.

Each plugin registers its commands when it is set up, each with its doc page. Refused, and the start with it: a command whose doc file does not exist, a name that is not lowercase letters, digits and dashes, a name another plugin or the core already registered (the message names both), and an `inJob` other than `true` or absent. Names are case-sensitive: `arthur Config` is not `arthur config`.

Inside a job, a process in the job's systemd scope `arthur-job-<id>.scope` while the home of the arthur.config.ts the CLI reads holds that job's record (`<home>/jobs/<id>`), or, where the job runs bare (no systemd user manager), one with `ARTHUR_JOB` set, which the wrapper sets to the job's record and a job's shell can clear (`arthur spawn --help`; docs/deploy.md, "Threat model"), only a command registered with `inJob: true` runs: `help`, `version`, `jobs`, `roles`, `remote-job` (its `records` step only), and of the plugins `decisions`, `board`, `task`, `plan` (orchestration), `findings`, `projects`, `machines`, `resources`, `stats`, `retro-due`, `health` (manage), `schedule` (its list only), `ci` (github, without `--rerun`), `youtrack` (reads only, its own refusal) and `plugin` (into the job's own worktree only, its own refusal). Every other command, `merge`, `spawn`, `continue`, `stop`, `stopall`, `steer`, `prune`, `send`, `ticket`, `review`, `review-needed`, `changelog`, `silent`, `coordinator`, `decision`, `init`, `restart`, `eval`, `run`, `setup`, `config`, `doctor`, `attach`, `retro`, `usage` and any a plugin adds without `inJob` included, is refused there: what the coordinator should do goes in the job's final message. `--help` and `arthur help <command>` still print any command's page. The plugins load first, as for any command, since a plugin's commands exist only once it is set up; the refused command then runs nothing. The mark is the variable alone: a job's shell that clears it is not told apart (AR0354).

Said, without running anything:

- Inside an eval session (`arthur eval --help`, of the develop plugin), where `ARTHUR_EVAL` names the eval's recording stub: every command, `help` and `--help` too, before anything else, `arthur: refused inside an eval session (ARTHUR_EVAL is set): arthur there is the eval's recording stub, <path>`; exit code 1.
- Inside a job (above), a command not registered with `inJob: true`, after its plugins loaded and before it runs: `arthur <command>: refused inside a job <id>: a job runs only the commands its role needs; put what the coordinator should do in your final message`, `<id>` the record's folder name; `schedule add` and `schedule remove`, `ci --rerun`, and each `remote-job` step but `records`, once their usage is right, say the same with the verb or flag after the command (`arthur schedule add: refused inside a job …`); exit code 1.
- An unknown command: `arthur: unknown command <name>`, then every command's name; exit code 2.
- When `arthur.config.ts` or a plugin does not load, only the core's commands exist (`config`, `continue`, `doctor`, `help`, `jobs`, `prune`, `remote-job`, `roles`, `run`, `send`, `setup`, `spawn`, `steer`, `stop`, `stopall`, `ticket`, `version`), and listing the commands says why. Of them `config`, `help`, `remote-job`, `setup` and `version` run as with the load, `arthur config check` and `arthur setup` reporting why it does not; past their own usage check, the others refuse, naming why, exit code 1: `continue`, `doctor` (after the core's requirements, when only a plugin did not load), `jobs`, `prune`, `roles`, `run`, `send`, `spawn`, `steer`, `stop`, `stopall` and `ticket`, as in `arthur ticket: the board needs the project list, and arthur.config.ts did not load:` and the reason.
- A doc file deleted after the command was registered: `arthur <command>: its doc file <path> was deleted after Arthur loaded`; exit code 1.
- `--project` without a name, or given twice: exit code 2.
- A `--project` name Arthur does not know, before any command runs (its `--help` still prints): with the list of the `projects` plugin, a name not in it, `arthur <command>: unknown project <name>; projects: <names>`; without that plugin, any name but the repository's folder name, `unknown project <name>; the only project is <name>`, or, outside Git, `unknown project <name>; no plugin provides the project list and <folder> is not in a Git repository`; exit code 1. When `arthur.config.ts` does not load, the project list is unknown and the name is not checked; the commands that read it refuse anyway.
- A command that throws: `arthur <command>: <message>`; exit code 1.

Phone commands: a command may also answer `/<name> <text>` on a channel, without the model. A channel routes the message to the host with where it came from, its channel, the place the message names (a topic, a channel id) and the channel's named instance it came through (a named bot), which the command gets beside the text, and sends the reply back to that place: the command's answer, `unknown command /<name>; phone commands: /a, /b` for a name no phone command has, or `/<name> failed: <first line of the error>` when it throws. A channel's command menu lists the phone commands, each with its one line. So that every phone command fits Telegram's menu, a phone command is also refused at start when its name has a dash or more than 32 characters, or its line is empty, only spaces, or longer than 256 characters; a command without a phone side keeps its dashes (`arthur review-needed`).

Exit code: 0 when the page or the list is printed, 1 when a doc file is gone, 2 on wrong usage or an unknown command.
