# arthur spawn

Usage: `arthur spawn <task> [--kind <name>] [--model <model>[,<model>...]] [--thinking <level>] [--timeout <minutes>] [--budget <usd>] [--machine <name>] [--requires <labels>] [--ignore-restart]`

Starts a job on the task, given as one quoted argument, and prints its id, `<date>-<kind>-<8 hex digits>` (the date in `core.timeZone`), for example `2026-10-16-worker-b046ca2a`. The job starts from HEAD of the repository that holds `arthur.config.ts`; uncommitted changes there stay where they are and are not in the job.

- `--kind`: the kind of job, default `worker`. The core owns `worker`; plugins register the others (review, audit, plan, ...).
- `--model`, `--thinking`: the agent's model and thinking level; left out, the role's (`arthur roles`), else the agent's own default. `--model a,b` is an ordered list, as a role's model may be (a plugin's `host.jobs.spawn` takes `model` as a name or a list): see "The model" below.
- `--timeout <minutes>`, `--budget <usd>`: the job's limits, a plain decimal of 0 or more such as `30` or `0.5`; `0` is no limit. Left out, the kind's own (`registerKind`'s `timeoutMinutes`, `budgetUsd`), else `core.jobs.timeoutMinutes` (default 120) and `core.jobs.budgetUsd` (default 2). A plugin's `host.jobs.spawn` takes them as `timeoutMinutes` and `budgetUsd` and is refused, before anything exists, for a value that is not a number of 0 or more: `spawn: <key> must be a number of 0 or more, got <value>`.
- `--machine <name>`: the machine the job runs on, `local` or one a plugin registered with `host.jobs.registerMachine` (below). Left out, the machine a plugin's `jobs.place` answers when one provides it (the `machines` plugin places each job by labels: `arthur machines --help`), else `local`. A plugin's `jobs.place` is asked about a named machine too and may refuse it, as `machines` refuses one without the labels the job needs; a named machine wins over what it answers. A plugin's `host.jobs.spawn` takes it as `machine`.
- `--requires <labels>`: the machine labels the job needs, such as `os=macos,tools=xcodebuild`: `os` and `arch` at most once each, `tools` once per tool (`tools=xcodebuild,tools=docker`), no spaces. They replace the ones of the job's ticket and project; how they are read is `arthur machines --help`. A plugin's `host.jobs.spawn` takes them as `requires`, `{ os?, arch?, tools? }`. Without a plugin that provides `jobs.place` the spawn is refused before anything exists: `requires: no plugin places jobs by labels (jobs.place); the machines plugin does`.
- `--project <name>`: the project, a name in the list of the `projects` plugin (`arthur projects --help`); the job starts from HEAD of that project's folder, and left out, of the first project in the list, the main one. An unknown name is refused, naming the projects (`unknown project <name>; projects: <names>`). Without the projects plugin, the only project is the repository of the folder Arthur runs in, named by its folder.
- `--ignore-restart`: a switch, no value; the `beforeSpawn` checks get it as `ignoreRestart: true`. The session plugin's restart guard then lets this one job start while a restart is due (`refused by session: restart due: ...`; `packages/session/docs/session.md`, "The restart guard"). Every other check still applies.

What it makes:

- A worker: the branch `arthur/<id>` and its worktree from HEAD. A read-only kind: a detached checkout of HEAD, no branch. Either lives in `.arthur-worktrees/<id>` in the folder that holds the repository, outside the main checkout and the home folder.
- No `node_modules`: the core copies none. A plugin's `prepare` step can install one (roadmap entry 41 gives the `projects` plugin a frozen-lockfile install); otherwise the job installs from the lockfile itself, as the worker's role tells it.
- The prompt of the kind's role, built from the role file, the project's override and criteria files in the worktree, and the sections plugins add; `arthur roles --help` says what goes in and in which order. A criteria file the project lacks, or an empty one, is a warning on stderr, `warning: <text>`, and the job starts.
- The job record `<home>/jobs/<id>/`, one file per key: `task`, `kind`, `model`, `model-why` (why the model was picked from its list, below; empty when nothing was picked), `thinking`, `quick` (the quick model, `--smol`; empty for none), `timeout` (minutes), `budget` (USD), `resume-on-budget` (`true` when the kind asks for one resume at its budget, else `false`), `cpu` and `memory` (the job's own caps, which a plugin's `jobs.limits` answers; empty for none: see "Caps per job" below), `idle-minutes` (`core.jobs.idleMinutes`, default 10), `branch`, `root` (the repository), `base` (the commit it starts from), `worktree`, `project`, `machine` (where it runs, `local` or another machine's name), `projects` (every declared project's main checkout at the spawn, a line `<name> <repository>` each, which the worktree guard refuses with each one's `.arthur-worktrees` when it cannot read the projects plugin's `<home>/projects/checkouts`, the same lines as declared now, which it reads on every tool call so a project added while the job runs is refused at once; a fallback is said once in the job's `log`; empty without a project list, and in the record on another machine, where every project's repository and worktrees are in the home folder), `prompt` (the role's prompt), and the state `working` (`state`, `reason` empty, `since`; see `arthur jobs --help`). An empty `branch`, `model` or `thinking` means none. The record appears whole: it is written under `.<id>` and renamed.
- Then each plugin's `prepare` step runs for the worktree (a hook to install, a file to place; on another machine through `host.jobs.run`, below), the event `job-started` is emitted with the job's `id`, `kind`, `project`, `root`, `branch`, `worktree`, `tickets` (the `Ticket:` files of the task) and `machine`, and the job's wrapper starts in the background. A `prepare` may return variables, `{ NAME: "text" }`, which go into the environment the wrapper and the agent run with, never into the record or the log, a later prepare's winning for a name; each prepare gets those the prepares before it returned as its second argument, `env`, in setup order (required plugins first, else the config's); anything else it returns refuses the spawn as a throw does, naming no value: `plugin <plugin>: prepare must return nothing or the job's variables, each a name of letters, digits and _ with a text`. `ARTHUR_AGENT_MODEL` among them is the model the agent gets in place of the record's (the models plugin's name of omp's provider); one in Arthur's own environment never reaches a job. `arthur spawn` waits until the wrapper wrote its `pid`, prints the id and returns without waiting for the agent.
- A worker's `job-started` moves each ticket its `Ticket:` files lie in (`spec/features/<id>-<slug>/...`) to `in-progress` on the board (see `arthur ticket --help`); a ticket already there is not written. A move the board refuses then, for a ticket changed after the spawn's check below, does not stop the job: it is printed as `plugin core: handler of job-started (event <n>) failed: <reasons>`. Other kinds move no ticket. `arthur continue` emits `job-started` again for each new run (see `arthur continue --help`).

Refused, before any worktree or record exists (exit code 1, the reason after `arthur spawn: `):

- An unknown kind: `unknown kind <name>; kinds: <registered kinds>`.
- A kind whose role no plugin registered, or whose role file is missing: `role <role> is not registered; roles: <roles>`, `role <role>: its role file <path> is missing`.
- An empty task: `the task is empty`.
- A worker in a repository with a branch named `arthur`, where Git cannot create `arthur/<id>`: `<repository> has a branch named arthur, so Git cannot create a worker's branch arthur/<id> beside it; rename it: git branch -m arthur <new-name>`. A read-only kind is not refused.
- A `Ticket: <path>` in the task whose file is not in HEAD, for example a ticket not committed yet: `Ticket: <paths>: no such file at HEAD (<commit>); commit it first`. Each `Ticket:` the task names is checked; the path ends at a space, and a closing `.`, `,`, `;`, `:`, `!`, `?` or `)` is not part of it.
- A plugin's `beforeSpawn` check that gives a reason: `refused by <plugin>: <reason>`; one that throws: `plugin <plugin>: beforeSpawn failed: <message>`.
- A worker whose `Ticket:` files lie in a ticket (`spec/features/<id>-<slug>/...`) that cannot move to `in-progress`: one in `planning`, not approved yet, a `merged` or `dropped` one, or one not on the board: `refused by core: <id> is <status>, which cannot move to in-progress` or `refused by core: <id> is not on the board`, one per ticket joined by `; `, then `; a worker starts on a ticket that is planned, in-progress, review, done`. Without a project list the board cannot be read: `plugin core: beforeSpawn failed: no project list: ...`. Other kinds are not checked.
- An unknown machine, named or placed: `unknown machine <name>; machines: <registered machines>`; two plugins that provide `jobs.place`: `call("jobs.place"): provided by <n> plugins; call needs exactly one`; a refusal of the plugin's `jobs.place`, as its own message (the `machines` plugin's: no machine with the labels, every one with them offline or full, a named one without them).
- On another machine (below): ssh refused, `machine <name>: ssh <ssh>: <ssh's last line>`, such as `kacper@gpu: Permission denied (publickey).` for a key the machine refuses or `Host key verification failed.` for an unknown or changed host key; `arthur` missing there, `machine <name>: arthur is not there (<the shell's line>); install the version here, <version> (docs/deploy.md)`; another version there, `machine <name> runs arthur <theirs>, this one is <ours>; both need the same version` (see `arthur version --help`).
- A project that is not the main one: `unknown project <name>; the only project is <name>`.
- A folder outside Git, or a repository with no commit yet.
- A config or a plugin that does not load: `arthur.config.ts did not load:`, then the reasons.

A `prepare` step that throws ends the spawn with `plugin <plugin>: prepare failed: <message>; the job's worktree and record were removed`: the worktree, its branch and the record are gone, and no `job-started` is emitted. The prompt's refusals end it the same way, before any `prepare`: an override or criteria file of the project that is a symlink, lies under one, or is not a plain file, which is never read (`<path> is a symlink; refused, the roles read a project's file only as a plain file; ...`), and a plugin's prompt section that is not text.

## The model

A spawn's model is one name, or an ordered list (a role's in `roles.model`, `--model a,b`, or a plugin's `host.jobs.spawn({ model: [...] })`); a spawn's own wins over the role's. The one plugin that provides `models.pick` (the models plugin, roadmap entry 82) is asked at every spawn with a model, after its machine is chosen and before any check or record: `models.pick(list, machine)` answers `{ model, why, free }`, the first available model of the list, the line why, and whether it costs nothing. The record's `model` is the model it answered and `model-why` the line, which `arthur spawn` prints on stderr as `model: <why>`; a free model's job has the budget 0 (no limit) whatever was asked, its time limit kept, and its `model-why` ends `; budget: none, free model <model>`. Refused before anything exists: the pick's own refusal (`no model available: ...`), an answer that is not `{ model, why, free }` naming a model of the list, two providers of `models.pick`, a model that is not a non-empty name or list of them, and, without a provider, any list: `a model list needs the models plugin`. Without the models plugin one name goes to the agent as it is. The job keeps its model to its end: a model lost mid-run fails the job with the agent's reason.

## On another machine

A plugin registers a machine with `host.jobs.registerMachine({ name, ssh, home, labels })` (roadmap entry 30 does it from the `machines` plugin's list): `name` in lowercase letters, digits and dashes; `ssh`, a `Host` of `~/.ssh/config` or a host name (letters, digits, `_`, `.`, `@`, `-`, not starting with `-`); `home`, the absolute path of Arthur's home folder there; `labels`, an object, read by placement. `local`, this host, is the core's and always registered. A name registered twice, `local` included, a bad `ssh` or a relative `home` is refused at registration, naming the machine: `machine <name>: registered by <plugin> and by <plugin>; a machine belongs to one plugin`, `machine <name>: ssh must be ...`, `machine <name>: home must be an absolute path, got ...`.

`host.jobs.machines()` answers the name of every registered machine, `local` first, then in the order they were registered (the resources plugin checks each one's free CPU and memory, roadmap entry 34).

A job on `local` takes no SSH step. A job on another machine takes every step there through `ssh -o BatchMode=yes -o StrictHostKeyChecking=yes -o ConnectTimeout=10 <ssh>`, so ssh never asks for a password nor accepts a host key on its own, and gives up on a machine that does not answer within 10 seconds, and through that machine's own `arthur` (see `arthur remote-job --help`):

1. `arthur version` there must print this core's version; then `arthur remote-job repo` creates the project's repository there, `<home>/repos/<project>.git` (bare), on first use, and says whether it holds the base commit. Only when it does not, `git push` sends it there over the same SSH, to `refs/arthur/base`. Every refusal so far comes before any record exists.
2. The prompt is built here, from the project's files in the main checkout. `arthur remote-job add` makes the worktree there, `<home>/repos/.arthur-worktrees/<id>` (on the branch `arthur/<id>` there, or detached), and its record `<home>/jobs/<id>/` there, `root` naming the repository there; then the record here, whose `worktree` is the path there and `machine` the machine's name.
3. Each plugin's `prepare` runs here, in this process, with the job's `machine` and its `worktree` there, and acts on the machine through `host.jobs.run` (below), such as the install of roadmap entry 41 in that worktree; nothing of a plugin goes to the machine but the variables a `prepare` returns (step 4). One that throws removes the worktree, branch and record there and the record here.
4. `job-started`, then `arthur remote-job launch` starts the wrapper there, with the env, worktree and steer extensions, in a scope of the slice `arthur-jobs.slice` there with the machine's own limit, its cores minus one and `MemoryMax` `70%` (this config's `core.jobs.cpu` and `core.jobs.memory` are this host's), running `core.agent.command` as that machine's `PATH` finds it. The prepares' variables go on its stdin, a JSON object, into the wrapper's environment there, never an argument or a file of a record. A wrapper that did not start there ends the job there, and the record here is copied at once.

`host.jobs.run(machine, argv, limitSeconds?, input?)` runs one command on a registered machine, `input` on its stdin (a secret goes there, never in `argv`, which a process list shows), and resolves, once it ended, to `{ code, stdout, stderr }`: its exit code (`null` when a signal killed it) and its whole output. On `local` it runs `argv` here, without a shell, and a command that does not start is code `127` with `<command>: <error>` on stderr. On another machine it runs over the same `ssh -o BatchMode=yes -o StrictHostKeyChecking=yes -o ConnectTimeout=10 <ssh>`, each word of `argv` single-quoted for the shell there, so spaces, quotes, `$`, backticks and newlines arrive as written; the command runs in the login's home folder there (a step in the worktree changes folder itself, such as `sh -c 'cd "$1" && npm ci' sh <worktree>`), and ssh's own failure comes back as code `255` with ssh's line on stderr. With `limitSeconds`, a command still running after that many seconds (ssh included, whatever it waits for) is killed (SIGKILL) and resolves at once with code `null`, the output so far, and `timed out after <limitSeconds> s` as the last line of stderr. An unknown machine is refused: `unknown machine <name>; machines: <registered machines>`; an empty `argv` or one with a word that is not text: `run: argv must be a non-empty list of words`; a `limitSeconds` that is not above 0: `run: limitSeconds must be above 0, got <value>`.

Arthur sends the machine the task, the prompt, the record's keys and the base commit, and a secret only as a `prepare`'s variable on the launch's stdin (a provider's key of the models plugin, for the job's agent). Each sweep of `arthur run` (every 30 s) copies, with one SSH call per machine, the files of the records changed there since the last copy for each of its jobs in a run, `root`, `machine`, `state`, `reason` and `since` excepted, and of the `log` only the bytes added since (the record's `synced` says where the next copy starts); a change of state moves the job here as there, with its `job-state` naming the machine. When the run ends there (`ended`, or `blocked`), its branch is fetched into the main checkout, `+refs/heads/arthur/<id>`, which updates a branch of that name left from an earlier run; then `state` is written and `job-ended` emitted. Any other failure of a copy is named in the run's log, and the other machines still copy; the dead-job sweep never ends a job on another machine. `arthur stop`, `steer`, `continue` and `prune` of a job on another machine run there (see each `--help`).

A machine that does not answer (ssh's exit 255: down, unreachable, its key refused) holds its jobs. At the first sweep that finds it so, each of its jobs in a run moves to `blocked`, reason `dependency: machine <name> unreachable since <time>` (UTC, ISO 8601), the time kept in the record as `offline`; there it runs on as it can. When the machine answers again within `core.jobs.offlineGraceMinutes` (default 30) of that time, each job takes the state its record there says: `working` or `idle` for one that ran on, its end and branch for one that ended, a plugin's hold for one held; nothing is started again. Once that time is `offlineGraceMinutes` ago, each such job ends here `failed: machine offline`, with one line in its log (`ended: failed: machine offline: machine <name> unreachable since <time>, past core.jobs.offlineGraceMinutes (<n>)`) and one `job-ended`; its worktree and record there are kept for the human, and `0` fails them at the first sweep that finds the machine unreachable. The sweep still follows such a job: once the machine answers and its run there has ended, its end and branch arrive as above, with a second `job-ended`, however late.

Wrong usage (no task, more than one, an unknown flag, a flag without a value or given twice, a `--requires` of another form: `--requires needs os=<os>,arch=<arch>,tools=<tool>, each label once but tools, got <value>`) prints the usage line and exits 2. Exit code 0 when the job was made and its wrapper started.

Each job runs in a systemd scope of its own, `arthur-job-<id>.scope`, inside the slice `arthur-jobs.slice`, which all jobs share: before the wrapper starts, `systemctl --user set-property --runtime` gives the slice a `CPUQuota` of `core.jobs.cpu` cores (as a percentage, at least 1%; default the host's cores minus one, at least one) and a `MemoryMax` of `core.jobs.memory` (default `70%`), and the wrapper starts through `systemd-run --user --scope`. Once the agent is done, before the end's files, the wrapper kills (SIGKILL) every other process left in the scope, a daemon that left the agent's process group included, so nothing the job started runs on once `state` is final. Where that `systemctl` fails (no user manager: macOS, a container) the job runs bare, outside any scope, and the first line of its `log` says so: `[arthur <time>] no systemd scope: <reason>; the job runs bare, without the joint limit of core.jobs.cpu and core.jobs.memory, and what it leaves behind is not killed at its end`.

A wrapper that does not start ends its job before `arthur spawn` returns: `systemd-run` fails or exits before the wrapper wrote its `pid` (it refused the scope, or is missing while `systemctl` is there), or no `pid` appears within 10 seconds, and then the process group is killed (SIGKILL). The record gets the end's files below, `result`, `activity` and `commits` empty, `cost` `0.0000`, `tool-calls` `0`, then `state` `ended` with the reason `failed: <reason>` last, the last line of `log` being `ended: failed: <reason>`, and `job-ended` is emitted; the worktree and branch stay for inspection. The reason is `systemd-run: <its first line on stderr>`, `systemd-run: spawn systemd-run ENOENT`, `the wrapper exited <code> before it wrote its pid; see <home>/wrapper.log`, or `the wrapper wrote no pid within 10 s and was killed`. `arthur spawn` prints the id, then `failed: <reason>` on stderr, and exits 1; `host.jobs.spawn` returns the reason as the job's `failed`, undefined when its wrapper started.

The wrapper, one background process per job, starts the agent, `core.agent.command` (default `omp`), in the worktree, in a process group of its own that the agent leads, with `ARTHUR_JOB` set to the record's folder: `<agent> -p --mode json --auto-approve --tools <tools> --append-system-prompt <record>/prompt -e <env guard> -e <worktree guard> -e <steer extension> [--model <model>] [--thinking <level>] @<record>/task`. A kind with a branch, such as `worker`, gets the tools `read,edit,write,bash,grep,glob`; a read-only kind `read,bash,grep,glob`. The env guard refuses a tool call that names a secrets file, the worktree guard one that writes outside the job's own place; the steer extension hands the agent the steers of `arthur steer` after each tool call (see `arthur steer --help`). Every run of the job loads all three, a resumed or continued one too. From what the agent prints the wrapper adds to the record, `log` appended to, every other file written whole under a temporary name and renamed:

- `pid`: the wrapper's process id, which `arthur stop` signals.
- `active`: written at the start; its modification time is the agent's last output, a line on stdout or stderr. After `idle-minutes` without one the wrapper turns the job `idle`, and the next one turns it `working` again (see `arthur jobs --help`).
- `log`: lines `[arthur <time>] ...` of the wrapper's own (the agent's command line, the end), one line per tool call (`<tool> <path, command or pattern>`), what the agent prints on stderr, and any line of its stdout that is not an event.
- `cost`: the USD the agent's messages report, summed, with 4 decimals; `tool-calls`: how many it started; `activity`: `tool` while a tool call runs, `think` otherwise.
- No `checks`: the core records no results of the project's own checks; roadmap entry 53 gives the `delivery` plugin an extension that does.
- At the end, every file above with its final value and `result` (the text of the agent's last message that had text, empty when none) and `commits` (a worker's commits since `base`, `git log --oneline`; empty for a read-only kind), then the state the run ends in, `reason` and `since` first and `state` last: `ended`, or `blocked` (below). A reader that sees one of them can trust every other file.

The run's outcome is `finished` when the agent exited 0 with a final message; otherwise `failed: <reason>`, the reason saying why: `the agent did not start: <error>`, `the agent was killed by <signal>`, `the agent stopped on error: <text>` or `on aborted` (the last message's stop), `the agent exited <code>`, `the agent ended without a final message`; or `stopped` (by `arthur stop`), `limit: time: ...`, `limit: budget: ...` or `limit: memory: ...` (below). The job ends `ended` with the outcome as its reason, except a `finished` run whose final message starts with a `Blocked:` line, which ends `blocked` (see `arthur jobs --help`). The last line of `log` is `<state>: <reason>`. Then the event `job-ended` is emitted with `id`, `kind`, `project`, `state` and `reason`, and `undelivered`, the numbers of the steers the agent never got, when there is one.

Limits: the wrapper stops a job at its limit with the stop of `arthur stop` (see `arthur stop --help`): SIGTERM to the agent's process group, SIGKILL to it when any of its processes is still alive 5 seconds later, then the processes that left the group and the rest of the job's scope; the log says `limit: time: stopping the agent`, `limit: budget: stopping the agent` or `limit: memory: stopping the agent`, and the job ends with the outcome of the first limit it reached, whatever the agent did after; an `arthur stop` after it (`arthur stop: asked as well`) leaves that outcome and rules out the resume below:

- `limit: time: the job ran past its timeout of <minutes> minutes`: `timeout` minutes after the wrapper started, even in the middle of a tool call, whose processes get the signal with the agent. When the time runs out while a job stopped at its budget is still ending, the log says `limit: time: reached as well`, and the job is not resumed.
- `limit: budget: its cost $<cost> reached its budget of $<budget>`: checked at each message the agent ends, once `cost` reaches `budget`, both at 4 decimals: a cost exactly at the budget stops the job, one $0.0001 below does not.
- `limit: memory: the job went over its memory cap of <memory>`: the job's own memory cap (below) was crossed; like the time, it rules out the resume.
- A kind registered with `resumeOnBudget: true` gets one automatic resume at its budget, unless its time is up as well: the log says `limit: budget: $<cost> reached $<budget>; the kind resumes once, its budget doubled to $<doubled>`, `budget` in the record becomes the doubled one, and the agent starts again in the worktree with `--continue` (its last session there, the job's own) and the message `Your budget of $<budget> ran out and was doubled to $<doubled>, once. Go on with the task where you stopped.` in place of `@<record>/task`. The cost keeps adding up from the first run, and the timeout still counts from the wrapper's start. A second time at the budget ends the job `limit: budget`; there is never a second resume. Other kinds, and a job stopped by its time, are not resumed.

A kind's `timeoutMinutes` or `budgetUsd` that is not a number of 0 or more, or a `resumeOnBudget` that is not `true` or `false`, is refused when its plugin registers it: `kind <name>: <key> must be ...`.

A record deleted while the job runs is noticed at the wrapper's next write: it sends SIGTERM to the agent's process group, so the agent and every process it started stop, kills what is left in the job's scope (a job that runs bare: one that left the group runs on), writes the one line `[arthur <time>] job <id>: its record <path> was deleted while it ran; the agent was stopped and nothing more is written` to `<home>/wrapper.log`, and ends; nothing more goes into the record's folder and no `job-ended` is emitted. `<home>/wrapper.log` also holds whatever a wrapper prints that has no record to go to, such as a crash.

## Caps per job

A job's own CPU and memory, inside the joint slice: what the one plugin that provides `jobs.limits` answers for the spawn, `{ cpu?, memory?, feature? }` (the `resources` plugin's `perJob`, and its caps per feature), kept in the record as `cpu`, `memory`, `feature`, `feature-cpu` and `feature-memory` (empty for none); `arthur continue` asks it again and writes its answer there, so a continued job gets the caps in force then. `feature` is `{ name, cpu?, memory? }`: the job's scope goes in the slice `<jobs' slice>-<name>.slice`, nested in the joint one, whose `CPUQuota` (at most the machine's cores) and `MemoryMax` (`infinity` when left out), with `MemorySwapMax=0` beside a `MemoryMax` so swap does not stretch it (`infinity` without one), are set before each launch, so all jobs of one ticket share them; a `name` that is not letters and digits refuses the spawn before anything exists: `jobs.limits: feature.name must be letters and digits, got <name>`. The record's `cost` starts at `0.0000` at the spawn. Without such a plugin the joint slice is a job's only limit; two that provide it refuse the spawn before anything exists: `call("jobs.limits"): provided by 2 plugins; call needs exactly one`.

- In the job's scope, on this host or another machine: `CPUQuota` of `cpu` cores, at most that machine's cores (`cpu: 64` on an 8-core machine is `800%`), so a job over it is slowed, not stopped; and `MemoryMax` of `memory` with `MemorySwapMax=0`, so the cap is not stretched by swap. When the job goes over it, the kernel kills one of its processes, as a rule the largest of the agent and what it started: the wrapper starts the agent with `oom_score_adj` 1000, which they all inherit, and keeps its own, so a second kill before the first one's memory is freed takes the agent, never the wrapper. From systemd 253 on the scope gets `OOMPolicy=continue`, so that kill does not stop the scope with the wrapper in it (an older systemd takes no `OOMPolicy` on a scope, and stops none). The wrapper reads the scope's `memory.events` every second: once it counts an `oom`, it stops the job with `limit: memory: the job went over its memory cap of <memory>`, a kill that ended the agent itself included. The other jobs run on.
- Over its ticket's `feature.memory`, the `MemoryMax` of the ticket's slice, the kernel kills a process of one of the ticket's jobs, the largest as above; a job with that cap gets `OOMPolicy=continue` too, its own `memory` or none. The wrapper also reads the slice's `memory.events.local` every second: once it counts an `oom` and the scope's `memory.events` an `oom_kill`, a process of this job killed, it stops the job with `limit: memory: the jobs of ticket <name> went over their memory cap of <memory>`. The ticket's other jobs, none of whose processes was killed, run on. Without a scope this cap is not held.
- Without a user manager (macOS, a container), where the job runs bare: the wrapper sums the resident memory (`ps` `rss`) of every process below it every 10 seconds, and stops the job with `limit: memory` at the first sample over the cap, a percentage being of the machine's memory; CPU is not capped. The caps of a ticket's slice (`feature`) are not held there at all. The first job with caps, its own or its ticket's, that runs bare on a machine emits a `notice`, once per machine (`<home>/uncapped` lists the machines told): `machine <name> runs jobs without a systemd scope (<why>): a job's memory cap there is held by sampling its processes every 10 s, its CPU is not capped, and a ticket's CPU and memory caps, shared by all its jobs, are not held`.
