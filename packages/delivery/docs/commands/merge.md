# arthur merge

Usage: `arthur merge <job> [--auto | [--unreviewed] [--no-ci] --decision <id>]`. Comes with the `delivery` plugin, `delivery()` in `arthur.config.ts`; its option is `merge.stepSeconds`, the time limit of each check on main (below, "Steps"), and `--auto` reads the project's `autoMerge` in the projects plugin's list (`arthur projects --help`).

Merges an ended job's branch into the branch its project's checkout has checked out, main, then does the rest of a merge's mechanical part. The job is its full id or the 8 hex digits that end it: a worker, or any job with a branch, an onboarding included. It commits nothing but the merge; main is pushed only by the plugin that provides `github.push`, when one is loaded; then the job and its ticket's other jobs are pruned (below, "Steps"). The procedure it prints last says what the coordinator does next.

## The PASS

A branch goes in only when its tip, the commit it merges, has a PASS: the newest review of that commit with a verdict says `PASS` (`arthur review --help`), or `arthur review-needed` answered `no review` for that commit (`arthur review-needed --help`). A commit after the PASS needs a new one. `--unreviewed` lets the branch in without it, only with `--decision <id>`, the owner's recorded decision (AR0355): `call("decision.owner", { id, what, kind: "merge", ticket, job, use })`, answered by the orchestration plugin (`arthur decision --help`, "What only the owner's decision lets through"), asked after the PASS and before CI; its refusal refuses the merge, `<refusal>; main is unchanged`. The decision lets through only the flags its `--what` names (AR0533). Without `--decision` it names the ask to make, `arthur decision ask --kind merge --what --unreviewed --question '<what he decides>' --ticket <id>` (`--job <id>` for a job naming no ticket); `outcome.md`'s `Reviews:` line then ends `; merged unreviewed (--unreviewed): no PASS on …`. An onboarding is never reviewed, so its merge, which only the owner decides, is always `--unreviewed`.

## Refused, touching nothing

Exit 1, main unchanged, nothing written or moved:

- No such job: `arthur merge: no job <name>; arthur jobs lists them`; a read-only one: `<id> is a <kind> job, read-only: it has no branch to merge`; one still in a run: `<id> is in a run (<state>); merge its branch once the run has ended`.
- Another `arthur merge` of the same project still running, from its first look at main to its end, its checks on main included: `a merge of <job> is in progress on <project>` (`a merge of pid <pid> …` in the moment before it names its job). Its merge commit is not checked yet, and a failed check resets main under anything merged on top of it, so the second merge is refused, not queued; run it again once the first has ended. The lock is `<delivery folder>/<project>/merge.lock`, its job in `merging` beside it; any end of the merge removes both, a refusal or a failed check included, and a merge whose process died (killed, a crash) leaves a lock the next merge takes over.
- The job's project not in the list; its branch not in the project's checkout: `arthur/<id> is not in <folder>: pruned, or not brought back from its machine`; a checkout on a detached HEAD: `<folder> has no branch checked out (a detached HEAD); check out its main branch first`.
- The project's checkout whose own Git config (`.git/config`, the main checkout's `config.worktree`, a file either includes) sets a key that may name a program, a filter, a merge driver, a credential helper or any key outside the set `docs/deploy.md` lists ("Threat model"), which a job's program can write; asked once the project is found, before any git call: `<file> sets <key>, which a job can write and which may name a program Arthur's git would run; remove it, or set it in your ~/.gitconfig; main is unchanged`. Asked again before the reset after a failed check: a key set meanwhile keeps main merged, `check failed on main (<command>), and main could not be reset to <commit>: <file> sets <key>, …`.
- Git with no identity for the merge commit in the project's checkout, author or committer, as `git var GIT_AUTHOR_IDENT` and `git var GIT_COMMITTER_IDENT` there find it (`user.name`/`user.email` of the repository, the user or the system, or `GIT_AUTHOR_*`/`GIT_COMMITTER_*`): `git has no identity for the merge commit: git var <variable> in <folder>: <git's last line>; set one: git config --global user.name "<your name>" and git config --global user.email "<your email>", or both with git -C <folder> config for this project alone; main is unchanged`. Arthur never sets one of its own. `arthur doctor` and the start of `arthur run` tell it earlier, before a review is paid for (below).
- A task naming several tickets: `<id>'s task names 2 tickets (…); a merge is of one ticket's branch`. Its one ticket not on the board; not `in-progress`, `review` or `done`: `AC0001 is merged; a merge is of a ticket in-progress, review or done`; or with an `outcome.md` already: `<folder>/outcome.md already exists: <id> was merged before`.
- A dirty main: `main has uncommitted changes in <paths>; commit or stash them first; main is unchanged`. The board, `spec/build.json`, does not count: the moves since the last commit wait there for the commit after a merge. Nor does `CHANGELOG.md`, which every merge rebuilds whole (step 7). Untracked files do not count either, filed reviews among them; `git merge` refuses one it would overwrite (below).
- A branch with nothing main lacks: `arthur/<id> at <commit> adds nothing to main (<commit>): nothing to merge`.
- Code that reached main by another route than `arthur merge`: a commit of main's first-parent line since the last merge `arthur merge` made, a merge made otherwise included, that changes a file outside `spec/`, `CHANGELOG.md` and `*.md` against its first parent, as `git log --first-parent <last merge>..HEAD -- . ':(exclude)spec' ':(exclude)CHANGELOG.md' ':(exclude)*.md'` lists them, the owner's own included: `main has <n> commits since its last merge that change code (<commits>); only a merge puts code on main; the owner decides, and arthur take-main lifts it: main is unchanged`, `<commits>` the newest 10 and then `and <k> more` when there are more (a history of plain commits, as squash or rebase merges and a solo project leave it, lists up to all of it). The last merge is the one each merge that went in records in `<delivery folder>/<project>/last-merge` (`.arthur/delivery/<project>/last-merge`, written under a temporary name and renamed), or the commit `arthur take-main` recorded there, so a merge commit a job makes on main hides nothing before it. Without that file, or with one holding no full commit hash, main's last merge commit counts (the root in a repository with no merge yet). One naming no ancestor of main's HEAD (main reset below it, or a commit this repository lacks) refuses (AR-D67): `main no longer holds <commit>, the last merge arthur merge made; only a merge puts code on main; the owner decides, and arthur take-main lifts it: main is unchanged`; one HEAD descends from only off its first-parent line (a merge made it a second parent) too: `main's first-parent line no longer passes <commit>, the last merge arthur merge made; …`, as above. `--unreviewed`, `--auto` and `--no-ci` lift none of these. The commit after a merge (the ticket's folder, the board, `CHANGELOG.md`) changes no code. The owner either takes the commits out of main (resets it to the commit before them, when main was not pushed with them) or, having read them, takes main as it is with `arthur take-main --decision <id>`, on his recorded decision (`arthur take-main --help`). A project whose history has no merge since its last code commit needs that before its first `arthur merge`.
- No PASS on the tip, without `--unreviewed`: `no PASS on arthur/<id>'s tip <commit>: <why> (last PASS: <commit>|none); review it with arthur review <id>, or merge it with --unreviewed --decision <the owner's decision id>; main is unchanged`, `<why>` being `no review of it has a verdict` or `its newest review, <review job>, says FAIL`.
- CI that failed, when a plugin provides `github.ci` (the github plugin) and without `--no-ci`: a run on the branch's own commits (a run further below the tip than the commits the branch adds ran on main and counts as none) that ended other than `success`: `arthur merge merges only with CI passed on the branch: run <id>, attempt <n>, on <commit>, the tip|<k> below the tip, ended <conclusion>: <url>; why: arthur ci <branch> --project <project>; or merge it with --no-ci --decision <the owner's decision id>; main is unchanged`. No run on the branch's own commits, one not finished, github not loaded or unable to tell: the merge goes on as without CI, waiting for nothing.
- `--no-ci` without the owner's recorded decision (AR0503): `--no-ci` asks no CI, so it goes on only with `--decision <id>`, checked as for `--unreviewed` (above, "The PASS"), `what` being `--no-ci`, after the PASS and before CI is asked; its refusal refuses the merge, `<refusal>; main is unchanged`, a decision of another kind, open or closed, of another ticket, used by another merge, or not asked with `--what --no-ci` (AR0533) included. Without `--decision` it names the ask to make, `--no-ci needs the owner's decision: arthur decision ask --kind merge --what --no-ci --question '<what he decides>' --ticket <id>, …`. With `--unreviewed` too, each flag asks for the decision, and only one asked with both, `--what --unreviewed --what --no-ci`, lifts both: the same merge passes it again. `--no-ci` never lifts the PASS: a branch without one is refused all the same.
- `collect("merge.check", job)`, asked last with the job as `arthur jobs` holds it (`id`, `kind`, `project`, `branch`, …): any text answer refuses, every answer named: `refused by merge.check: <answer>; <answer>; main is unchanged`. The projects plugin answers for an onboarding, whose branch may change only the vision and the criteria files (`arthur init --help`).

Wrong usage (no job, two, an unknown flag, `--auto` with `--unreviewed` or `--no-ci`, `--decision` without `--unreviewed` or `--no-ci`, or without a value) prints the usage line and exits 2.

## --auto

The merge without the owner, after a PASS and green CI. On top of the refusals above, and in place of the PASS above, each refusal naming its rule, exit 1, main unchanged:

- The project's `autoMerge` not `true`: `--auto merges only in a project with autoMerge on; <project> has autoMerge false|unset, so its merges wait for the owner: arthur merge <job> on his word`.
- No PASS on the tip itself (`arthur review-needed`'s `no review` does not count here): `--auto merges only with a PASS on the tip: arthur/<id>'s tip <commit>: <why>; review the tip: arthur review <job>`, `<why>` being `no review of it says PASS`, `its newest review, <review job>, says FAIL`, or `the last PASS, <review job>, is on an older commit, <commit>`.
- A held path among the files the branch changes from where it left main (both names of a renamed file): a role (any `roles/` folder, and the project's `prompts.rolesDir`, default `.agents/arthur/roles`), the vision (`prompts.vision`, default `spec/vision.md`), CI (`.github/workflows/`), any `package.json`, or a file on the always-review list (`review.alwaysReview`, `arthur review-needed --help`): `--auto merges no held path: arthur/<id> changes <path> (a role|the vision|CI|package.json|the always-review list); its merge waits for the owner: arthur merge <job> on his word`.
- No plugin provides `github.ci` (the github plugin not loaded, or disabled): `--auto asks CI of github, which is not loaded (…); without it, only the owner's decision merges: arthur merge <job> --no-ci --decision <the owner's decision id>`. `--auto` never goes with `--no-ci` (wrong usage, above): a merge without CI is the owner's, on his recorded decision.
- CI not passed on the tip itself, as `call("github.ci", { project, branch })` answers: the run that built the branch, as `arthur ci` finds it (`packages/github/docs/commands/ci.md`); a run below the tip, on main or on an older commit of the branch, counts as none (AR0359), and so does a run whose commit is not the tip delivery read, even one github puts 0 below it (AR0437). The cost: a tip no run builds (pushed with `[skip ci]`, or left out by a workflow's `paths-ignore`, such as a docs-only commit) never passes, so its branch waits for the owner's `--no-ci --decision <id>`. Each `--auto merges only with CI passed on the branch: …`: `github could not tell: <github's refusal>`; `run <id>, attempt <n>, on <commit>, the tip, ended <conclusion>: <url>; why: arthur ci <branch> --project <project>`; or, for a run on the tip not finished or none on it yet, `…, is queued|in_progress` and `no run built the tip yet`, with `(the nearest, <id>, ran on <commit>, <k> below the tip|not the tip <tip>)` when there is one, each ending `; it waits: when that run ends, the coordinator is woken with its verdict`.

A wait is `<delivery folder>/<job>/ci-wait`. When the github plugin's poll sees a run end on the branch (`ci-finished`), it asks `collect("delivery.ciEnded", { project, branch, below, run })`; a run on the branch's tip (`below` 0), or one delivery cancelled at any depth (AR0437), its tip still the one that waited and its job not pruned, gets one `coordinator-message`, delivery's (marked `[Arthur: delivery]`), and github's own wake leaves the branch out (AR0257), once per run attempt (a rerun's end again), across a restart too (`<job>/ci-told`): `CI passed on arthur/<id> (run <id>, attempt <n>, on <commit>): <url>. It waited for that: arthur merge --auto <job>`, or `CI ended <conclusion> on …. Not merged; it waits on: …. Why: arthur ci …; then` what to do for each case, as `arthur ci --help` says: a failure in the branch's own code to its worker with `arthur continue <job> '<the failed step and its lines>'`, one that looks transient rerun once with `arthur ci … --rerun`. Any other end, one below the tip included, is github's to tell. While `arthur run` runs, delivery also asks `github.ci` for each wait every minute: a run on the branch's own commits, the tip or one below it, not finished 30 minutes after its start is cancelled once through `call("github.cancel", { project, run })`, since a hung one may hold the runner the tip's run waits for; its end then says `cancelled by delivery after it ran 30 minutes`, and a cancel GitHub refuses wakes the coordinator with the refusal and the run's page. A wait ends when the branch is merged, its job is pruned, or its branch moves past the tip that waited; a broken wait file is said once on stderr.

## Steps

Each printed as it is taken:

1. `git merge --no-ff -m "Merge <ticket>: <title>" <tip>` (`Merge arthur/<id>` for a job naming no ticket), then `merged arthur/<id> into main: <hash>`. A conflict aborts the merge, `arthur/<id> conflicts with main in <files>; merge aborted, main is unchanged`; any other failure of `git merge` is `git merge arthur/<id> failed: <git's last line>; main is unchanged`.
2. Checks on main. Each step runs in a transient systemd scope of its own, `arthur-merge-<pid>-<n>.scope`, under the jobs' slice `arthur-jobs.slice`, as a job does, and the scope is stopped once the step ended, so what the lifecycle scripts of an install or the `check` and `test` scripts leave running is killed before the next step. Where no user manager can make one (a container, macOS, inside a job's sandbox), the steps run bare, which one line says before them: `uncapped: no systemd scope (<why>); the steps run bare, outside the jobs' slice, and what they leave behind is not killed`. Each step also runs in a sandbox of its own, the one a job's install runs in (`arthur spawn --help`, "The sandbox"): it writes only in main's checkout as the next sentences say, the merge's own cache folder, the temporary folder and `/dev`, reads every file but the env file (`core.envFile`) and `~/.ssh`, reads no other process's environment (`arthur run`'s, the coordinator's, this merge's), and opens no Unix socket but a datagram one, so the branch's code the checks run (an install's lifecycle scripts, the `check` and `test` scripts) reads no secret of Arthur's. The package managers' caches are that folder, `<delivery folder>/cache_<random>`, made before the first step and removed after the last, whether the merge went in or not (one an `arthur merge` killed during its steps left is removed at the start of a later merge once older than a day, to the minute; a younger one may be a running merge's. Its `_` is in no project's name, so a project's own folder there, `last-merge` and all, is never one); the reinstall below gets a fresh one of its own, removed after it, so main's install takes nothing the branch's left in the merge's: each step runs with `npm_config_cache`, `BUN_INSTALL_CACHE_DIR`, `XDG_CACHE_HOME` (pnpm's and uv's), `PNPM_HOME` (pnpm's store) and `COMPOSER_CACHE_DIR` pointed into it, so a step writes none of the shared caches (`~/.npm`, `~/.cache` and the like), where the branch would leave what a later process outside any sandbox runs, such as an `npx` package in `~/.npm/_npx`; each merge's install starts with a cold cache. In main's checkout a step writes each entry but `.git`, and but Arthur's home (`core.home`), `arthur.config.ts` and the env file where one sits inside the checkout; of `.git` only `objects`, `refs`, `logs` and the `index` file in place, never its `config`, `hooks` or `info`, so a step plants no hook or `core.fsmonitor` that your next git call there would run outside any sandbox: such a write fails `Permission denied` (`git config` prints `could not lock config file .git/config: Permission denied`). Git's own update of the index or `HEAD` goes through a lock file in `.git` and is refused too, so a step's `git add` or `git commit` fails. The checkout's own folder, and each folder on the way to a path it keeps (`ops/` for a home in `ops/.arthur`), takes no new entry and loses none: a step writes a top-level file or folder that is there, but making one (`dist/`, `coverage/`, `tsconfig.tsbuildinfo`), or renaming or removing one, fails; make it once outside a step (`mkdir dist`) and keep it in `.gitignore`. A symlink there opens no write where it points. Which entries those are is read before the merge's first step, and again before the reinstall below. A step still writes the folders below the top, where it could make a repository of its own (`git init src`) or a `.git` file pointing to one elsewhere, untracked, so the reset after a failed check keeps it, whose `core.fsmonitor` or hooks your next git call in that folder would run outside any sandbox. Git also takes a folder holding a `HEAD` as a repository's Git folder whatever its name (`git init --bare src/cache`, then `core.bare false` and a `core.worktree`), and follows a symlink to one elsewhere (`src/link`, to a repository outside the checkout or a folder in its `.git`). So after each step, passed or failed, with the sandbox or without it, every repository below the checkout's top that was not there, the same, in main's checkout just before `git merge` is removed, one line each, so one the branch itself commits counts as a step's and goes after the first step (AR0490): main's checkout then lacks that tracked file, which `git status` shows and the next `arthur merge` refuses as an uncommitted change until you restore or remove it, and checks that need it, a Git folder kept as a test fixture, fail. Those are: a `.git` (a folder, a file or a symlink), a folder holding a `HEAD`, and a symlink to a folder outside the checkout or in its `.git`, or a dangling one that points there, where a folder may come later, followed from its folder's real path as the kernel follows it, also where the checkout's own path goes through a symlink (a symlink to a file, a venv's `python`, or to a folder inside the checkout stays, and so does any symlink there before `git merge` and the same, whatever its target became, but one into a folder a step writes, the checkout's `.git`, the temporary folder, `/dev` or `<delivery folder>`, where the merge's caches go, or that passes through a symlink there anywhere on its way (followed link by link, up to the kernel's 40), which a step can point elsewhere, is judged by its target and each link on its way too, and by the `.git` and `HEAD` in each folder above its target and above each link down from that folder, where git walking up from the target would find a repository a step made: a file there a step replaced, a folder there it wrote in, or a dangling one's target it made changes it, and one whose target Arthur's user cannot read whole is removed after the first step, `removed <path>, which <command> left: its target, in a folder a step writes, could not be read, so a repository there could not be told from the owner's own`; one an install makes to a folder outside, an npm `file:../sibling` dependency or a global pnpm store, is removed): `removed <path>, which <command> left: a git call in that folder would run its config outside any sandbox`, or, when it stays, `<path>, which <command> left, could not be removed (<why>): a git call in that folder would run its config outside any sandbox`. A `.git` that was there before, a submodule's or a clone of your own, stays while a step only reads it with git: an `index` git rewrites there (`git status` refreshes one, a linked worktree's in `worktrees/<name>/` too), its `sharedindex.<hash>` under `core.splitIndex`, and a lock file git makes and removes in the `.git` folder or one holding an index do not count, where `python3` reads those folders' extended attributes, an ACL among them, so a change of them still counts (where `python3` fails, a git read there counts as a change: a failed read after a step is tried once more first, and a `.git` that was there before is then removed with `removed <path>, which <command> left: python3 failed to read the extended attributes of its Git folders, so a git read there could not be told from a change`, or the same reason after `could not be removed (<why>)`). One a step replaced, or in which it added, removed or rewrote any other file (its `config`, a hook) or changed a folder's permissions, owner, group or ACL, is removed; a folder a step made unreadable or unwritable to keep one gets its owner's read and write back first. A check that needs a Unix socket (a tmux server, a database's local socket, Docker, the user manager's bus) fails there or skips, as it would inside a job. Where the sandbox cannot be set up (not Linux, no `python3`, a kernel without Landlock), the steps run as before, their caches in the merge's folder all the same, which one line says first: `no sandbox: <why>; each step writes wherever Arthur's user can`. Every step runs on the PATH the plugin that provides `nvm.path` (the nvm plugin) answers for `{ root }`, main's checkout: the bin of the Node its `.nvmrc` names first, as a worktree there gets it; `""`, or no plugin providing it, runs them on the PATH `arthur merge` has. A throw of `nvm.path` (that Node not installed, nvm missing) runs nothing and is a failed step: `node: failed, <message>.`. First the project's install, the one a new worktree of the merge commit gets, as the plugin that provides `projects.install` (the projects plugin) answers for `{ project, commit: "HEAD" }`: the project's `install` in `arthur.config.ts` when set, else the frozen install of its one known lockfile (`arthur projects --help`, "Install"); `install: ""`, or no lockfile and no `install`, runs nothing. A throw of `projects.install` (two known lockfiles and no `install`, or no plugin providing it) runs nothing and is a failed step: `install: failed, <message>.`. Then `npm run check` and `npm test`, each only when main's `package.json` declares its script; with neither, and no install, `no checks: package.json declares no check or test script`. Each prints `<command>: passed.`, `12/12 passed.` or `failed, 11/12 passed.` (the counts from node --test's last summary, when it printed one), and a failed one its last 20 lines. Each step has `merge.stepSeconds` (delivery's option, default 3600, an hour) to end: one still running then is killed, SIGKILL to its process and then its scope stopped, and fails, `<command>: failed, timed out after <n> s.`; run bare, what it started may live on, as the `uncapped:` line says. A failed `nvm.path` or install, or a `package.json` that is not JSON, ends the steps.
3. Records the merge commit in `<delivery folder>/<project>/last-merge` (above, "Code that reached main by another route"). For a job naming no ticket: `no ticket: no outcome.md, nothing moved`, and the merge goes on at step 7. Otherwise, files every review of the branch with a verdict that no `review-N.md` of the ticket names yet, as `arthur ticket file` does: `filed <path>`, or `review <job>: not filed: <why>` (a pruned review's result is gone).
4. Hands the ticket's findings to the plugin that provides `findings.onMerge` (the findings plugin), asked with `{ project, ticket, path, root }`, `path` the ticket's `findings.md` from the project's folder whether it exists or not; its answer is the lines of `## Left open`, printed. With no provider the findings stay as they are and the merge says so once: `- Findings: <path> left as it is, every open entry still open: no plugin provides findings.onMerge`, or `- Findings: none; no findings.md on this ticket.` without the file. A provider that throws costs its own line: `- Findings: findings.onMerge of <plugin> failed: <message>; <path> left as it is`.
5. Writes `outcome.md` in the ticket's folder, in the shape of the core's template: `- Merged: <date>, <hash>`, `- Branch:`, `- Reviews:` (the branch's `review-N.md` files with their verdicts), `- Cost: worker $x, reviews $y; review rounds N` (delivery keeps a review's cost in its own record of it when its run ends, so a review pruned after that still counts; `n/a` when the worker's job record or its cost is gone, or a review was pruned and delivery's record of it holds no cost, as one kept before AR0474 does), the commit subjects under `## What went in`, each step under `## Checks on main`, and step 4's lines under `## Left open`.
6. Moves the ticket to `merged` (`ticket-moved`, named by delivery), `<id> merged`, and names the `planned` tickets whose `after` it completed: `unblocked: <id>, <id>`.
7. Rebuilds the project's `CHANGELOG.md` from its merged tickets, as `arthur changelog` does (`arthur changelog --help`): `wrote CHANGELOG.md: <n> merged tickets`.

Then, when a plugin provides `github.push` (the github plugin, `packages/github/docs/github.md`, "Pushes"), main is pushed to origin and that plugin's one line printed, `github: pushed main to origin: <old>..<new>` or the warning `github: main not pushed to origin: <why>` (a push rejected as non-fast-forward, no origin), which leaves the merge in: it is never retried and never asks for a password. Then the merged job and every job whose task names a file of its ticket's folder are pruned, as `arthur prune <id>...` prunes them (`arthur prune --help`), a line each, `<id>: <what was done>`: their worktrees, the branches main now holds, their records, and what each plugin frees with them (`jobs.keep`: delivery's own folder of the job, `<delivery folder>/<id>/`, while its record of a review, `reviews/<id>.json`, stays; the github plugin's delete of the branch on origin, `packages/github/docs/github.md`, "Branches on origin"). A job in a run, held or blocked is kept (`kept: it is <state>, not ended`), and so are a worktree with changes and a branch main does not hold, as the prune says, and a worker delivery still hands back after a FAIL review (`<id>: kept: delivery still hands it back after a FAIL review; arthur prune <id> once that ends`); main is pushed before, so origin has the commits of a branch it deletes. Last, `nothing committed but the merge` (`nothing committed but the merge, nothing pushed` without that plugin) and the procedure after a merge, `packages/delivery/roles/coordinator/after-merge.md`. A merge that refuses or fails prints none of these and pushes nothing.

## When a check fails

Main goes back to the commit before the merge with `git reset --keep`, which keeps the board's uncommitted moves; nothing is filed or written and no ticket moves. When an install ran in the steps, main's own is run again, as `projects.install` answers for main's HEAD after the reset, on the PATH `nvm.path` answers for it then, `reinstall of main's dependencies, <install>: passed.` or `failed.`. It runs over a fresh cache folder, `<delivery folder>/cache_<random>` again, removed after it, in a sandbox of its own, so a host without the sandbox prints its `no sandbox:` line a second time before it; its step is swept for a repository against the same look before the merge's first step as the checks were, so one that appeared since (a process a check left running, bare, may write one) is removed after it too. Exit 1 with `check failed on main (<command>); main reset to <commit>, branch kept`, ending `, but reinstalling main's dependencies failed (<install>): they still hold the branch's install` when that install failed. When the reset itself fails: `check failed on main (<command>), and main could not be reset to <commit>: <git's last line>`.

## What the coordinator does with the result

- A merge that went in ends with the procedure: follow it in the same turn.
- `github: main not pushed to origin: …`: the merge is in; follow the procedure, whose push after the board's commit is the next try, and tell the owner the line if that push fails too.
- `a merge of <job> is in progress on <project>`: main is unchanged; follow that merge to its end, then run this one again.
- `check failed on main (…)`: main is as it was. Tell the owner which check failed, its command written out as the brackets name it (`npm test`), with its last lines; run `arthur continue <job> '<what failed>'` without asking him, and start a new review once it ends.
- A conflict, `refused by merge.check: …` or `git has no identity …`: main is unchanged; tell the owner, in plain words, with the fix the line names.
- `main has <n> commits since its last merge that change code …`, `main no longer holds …` or `main's first-parent line no longer passes …`: main is unchanged; tell the owner the commits, with their subjects (`git log --oneline <commits>`); the merge waits for his decision above (`arthur take-main --decision <id>` once he keeps them), and the branch goes in once he has made it.
- `no PASS on …`: review the branch (`arthur review <job>`), or ask the owner for `--unreviewed`: record his decision first (`arthur decision ask --kind merge --what --unreviewed …`, then `answer`), and merge with `--unreviewed --decision <its id>`.
- `arthur merge merges only with CI passed on the branch: run …, ended <conclusion>`: tell the owner, with what its `why:` command says; the branch goes in only with `--no-ci` on his recorded decision: record it first (`arthur decision ask --kind merge --what --no-ci …`, then `answer`), and merge with `--no-ci --decision <its id>`.
- `--auto merges only with CI passed …; it waits`: nothing to do until the wake with CI's verdict; after `CI passed`, `arthur merge --auto <job>` again; after `CI ended <conclusion>`, as the next line.
- `--auto merges only with CI passed on the branch: run …, ended <conclusion>`: run its `why:` command; a failure in the branch's own code is handled as a failed check above, `arthur continue` without asking included; one that looks transient is rerun once (`arthur ci --help`).
- Any other `--auto` refusal: the merge waits for the owner; tell him the rule it named.

## arthur doctor

The plugin gives `arthur doctor` one requirement per project, never critical: `delivery <project> identity: ok`, or `delivery <project> identity: missing: git var <variable> in <folder>: <git's last line>; without it: arthur merge refuses every branch of <project>: git has no author for the merge commit; fix: <the fix above>`, the same check as the refusal above. So a machine with no identity hears it at `arthur doctor`, `arthur setup` and each start of `arthur run`, before the first merge.
