# The delivery plugin

Review and merge of a worker's branch: a plugin, not the core, which stays a job runner. `arthur review <worker job>` starts a read-only review of the branch's tip on the reviewer role (orchestration's `roles.reviewer`); its verdict, PASS or FAIL, moves the ticket, a FAIL hands the work back to the worker, and after 4 FAILs since the branch's last PASS the next review waits for the owner's word. `arthur review-needed` says whether a branch needs a review at all; one that changes a file on the always-review list always does. `arthur merge` merges a branch with a PASS into main and runs the checks on main; for a project with `autoMerge` (its piece, `delivery.project({ autoMerge: true })` in its project file) `arthur run` runs it on its own after a PASS or a `no review`, and it merges once CI passed (`arthur merge --help`, "On its own"). `arthur take-main` takes main as it is, on the owner's word, `arthur changelog` writes `CHANGELOG.md` from the merged tickets, as each merge does, and `arthur commit-board` commits the board's files alone, after the project's own commit check, in place of the coordinator's `git commit`.

```ts
plugins: [orchestration({}), projects({ folders: [...] }), delivery({ review: { alwaysReview: ["**/env.ts", ".github/workflows/**"] } })],
```

## Options

- `review.alwaysReview`: the files a branch that changes one always gets a review for, in every project, as glob patterns from its root; a list replaces the default, which holds what reads secrets, the CI's workflows and its handling, the review rules, the prompt files every role reads, and what a merge and each spawn run (`arthur review-needed --help`, "The always-review list").
- `merge.stepSeconds`: the seconds each step of `arthur merge`'s checks on main (the install, `npm run check`, `npm test`) may run before it is killed and fails the merge; default 3600, an hour (`arthur merge --help`, "Steps").

An unknown option or key, a pattern that is empty or starts with `/`, or a `stepSeconds` that is no whole number of 1 or more, refuses the load.

Each command's page, what `arthur <command> --help` prints, is in [`commands/`](commands/).

## A ticket's jobs

AR0555: what a ticket's jobs hold goes once the ticket needs them no more. `arthur merge` prunes the merged job and every job of the ticket after it pushed main (`arthur merge --help`, "Steps"). A ticket moved to `dropped` (`ticket-moved`, from `arthur ticket status <id> dropped`) prunes every job of the project whose task names a file of the ticket's folder, as `arthur prune` prunes them; a branch Git kept because main does not hold it, of a job that ended on this machine, is then deleted with `git branch -D` when it is `arthur/<id>`, the one the job's spawn made (a record naming another keeps it, and the prune's line says why, AR0610), and the job pruned again, so its commits go with the ticket, and the github plugin deletes its copy on origin when origin's tip is the one it pushed (`packages/github/docs/github.md`, "Branches on origin"). A worker delivery hands back after a FAIL review (`arthur review --help`, "Hand-back") is handed back no more: its hand-back ends, so one not in a run is pruned as the others are, and a hand-back that a FAIL of the dropped ticket would start, starts not; the coordinator is never told to hand it back. A job in a run is kept, `<id>: kept: it is in a run; once it ends, delivery prunes it, its branch too`: its end (`job-ended`, while `arthur run` runs, or at its next start) prunes it as the drop did, an unmerged branch included, once every plugin has read the ended job (the coordinator's wake reads its final message first). A blocked job keeps everything until it ends, and a worktree with changes keeps its branch, checked out there. A repository whose own Git config sets a key that may name a program keeps every unmerged branch, and nothing is run. Each line goes to the log, `delivery: <ticket> dropped: <prune's line>`, then `<branch> deleted, not merged: <ticket> is dropped` and the second prune's line; or `kept every unmerged branch: <file> sets <key>, …`.

Each prune also removes delivery's own folder of the job, `<home>/delivery/<id>/` (its recorded checks, a CI wait, the causes it merged on its own), and `arthur review-needed`'s answer of it, `<home>/delivery/review-needed/<id>.json`, through `jobs.keep`; delivery's record of a review, `<home>/delivery/reviews/<id>.json`, stays, for the FAIL counts and the costs in `outcome.md`.

## Processes a job leaves running

AR0585: when a run of a job is about to end, at omp's `session_stop`, which comes right before `agent_end` and before the run's last message counts as the job's result, delivery's OMP extension, `packages/delivery/src/checks-extension.ts`, which every job's agent loads with `-e`, lists the job's processes other than the agent and its wrapper (the agent's parent), as `packages/delivery/src/processes-extension.ts` finds them: in the job's systemd scope, `arthur-job-<id>.scope` (`arthur-job-<id>.<ms>.scope` for a continued run), every process of the scope, a daemon that left the agent's process tree included; in a job that runs bare, the agent's descendants, as `ps -A` shows them. When there are any, the run goes on with one message, `[Arthur] Before your run ends: these processes of your job are still running.`, a line `- pid <pid>: <command line>` for each, and the ask to stop each one it started and no longer needs, then to end with its final message again, whole, since the job's result is its last message. Each `@` that starts a word of a command line gets a word joiner (U+2060) before it, so omp reads no file it names. With none, or without `ps`, nothing is said of them.

AR0675: the run's end gets one answer, from one handler, as omp keeps only the first continuation its `session_stop` handlers give. A worker whose checks have not passed on its clean committed tip is reminded of them at the same moment (AR0656: `[Arthur] Before your run ends: Arthur starts no review yet: ...`, with what `arthur review` would refuse and what to run); when both reminders are due, the run goes on with one message that holds both, the checks' first, a blank line, then the processes'. With neither due, the run ends.

Each of the two is given at most once per run, one omp process: a run's end that got only one may be followed by an end that gets the other, and the end after both were given, the run's third at the latest, is its end, processes left and checks missing or not, so the reminders never loop; `arthur continue` and a resume start a new run, which may get them again. The extension only reminds: it stops nothing, and the wrapper still kills every process left in the job's scope when the job ends (`arthur spawn --help`). A job whose record was written before AR0675 names `processes-extension.ts` as an extension of its own, and each later run of it still loads the file, which registers nothing.
