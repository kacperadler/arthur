# arthur dokploy

Usage: `arthur dokploy apps [--instance <name>]`; `arthur dokploy app [<app>] [--instance <name>]`; `arthur dokploy status [<app>] [--instance <name>]`; `arthur dokploy upload [<app>] <file or folder> [--instance <name>] [--replace-source]`; `arthur dokploy deploy [<app>] [--instance <name>]`; `arthur dokploy create <name> --dokploy-project <name> [--environment <name>] [--instance <name>]`; `arthur dokploy setup <app> [--dockerfile <path>] [--context <path>] [--domain <host> --port <n>] [--volume <name>:<path>] [--instance <name>]`; `arthur dokploy env <app> names [--instance <name>]`; `arthur dokploy env <app> set <NAME> <value> [--instance <name>]`; `arthur dokploy source <app> --repo <owner>/<name> --branch <branch> [--build-path <path>] [--github <name>] [--replace-source] [--instance <name>]`; `arthur dokploy postgres create <app> <name> [--version <n>] [--env <NAME>] [--instance <name>]`; `arthur dokploy postgres status <postgres> [--instance <name>]`; `arthur dokploy postgres backup <postgres> --destination <name> --schedule "<cron>" [--keep <n>] [--instance <name>]`; each with `--project <name>` for another project than the main one.

The `dokploy` plugin reads the owner's Dokploy servers (AR0588): their projects, applications and deployments, on the instance a call names or a project's piece, `dokploy.project({ instance?, app })`, picks; and, on the owner's word, uploads a file or folder to an application or starts its deploy (AR0603), creates an application and sets its build type, domain, volume and environment (AR0654), connects an application to its GitHub repository, so a push deploys it (AR0680), makes a Postgres beside an application, connected to it (AR0681), and schedules its backups to an S3 destination (AR0682). Every call goes to `<url>/api/<procedure>` of the instance's configured `url`, with its token as the `x-api-key` header; a redirect is never followed, so the token goes nowhere else.

Only the coordinator runs it: inside a job the command is refused before it acts (`arthur dokploy: refused inside a job <id>: ...`), and a job's CLI reads no env file, so the token is not there either.

## Reading

- `apps`: every project of every instance, under a heading `instance <name>` (`instance (unnamed)` for the unnamed one), a blank line between two instances; with `--instance`, only that instance's. Each project is `project <name>`, then each environment, `  environment <name>`, then its applications, one line each: `    <applicationId> <name> (<applicationStatus>)`. A project or an environment without applications is still listed, with `: no applications` after it; an instance without projects says `no projects`. A server that answers the applications right under each project, as the example of Dokploy's documentation shows, gets them right under the project. An instance that fails prints its error line on stderr under its heading, the others still print, and the exit code is 1. Dokploy: `GET /api/project.all` ([Dokploy API](https://docs.dokploy.com/docs/api), [project](https://docs.dokploy.com/docs/api/project)).
- `app [<app>]`: one application: its name, id and instance; its project and environment; its `sourceType` and `applicationStatus`; its domains as URLs (`https://shop.example/admin`), or `none`; its last deployment by `createdAt`, as `status` prints one, or `none`. Nothing else: never its env, build args or secrets, preview env, git refresh token, registry password or server. Dokploy: `GET /api/application.one?applicationId=<app>` ([application](https://docs.dokploy.com/docs/api/application), "Application one").
- `status [<app>]`: `<name> (<id>) on instance <name>: <applicationStatus>`, then the 5 newest deployments by `createdAt`, one line each, `<status>: <title>, started <time>, finished <time>` (`not yet` for a time Dokploy has not set), then Dokploy's error message of that deployment when it has one, each of its lines after `  > `: what Dokploy said, as data; `no deployments` when there is none. Dokploy: `application.one`, then `GET /api/deployment.all?applicationId=<app>` ([deployment](https://docs.dokploy.com/docs/api/deployment), "Deployment all").

## Writing

Only when the owner asks: an upload or a deploy changes what his server runs. Each prints where it went and the call that follows the deployment Dokploy queued, picking the app the way this call did: `arthur dokploy status`, with the `<app>`, `--instance` and `--project` given.

- `upload [<app>] <file or folder>`: sends the code of a drop application, which Dokploy unzips into the app and then deploys. A file named `.zip` that starts as a zip does (`PK\x03\x04`) goes as it is; any other file, or a folder, is zipped first: a folder's regular files go at the zip's root by their path inside it, a file goes there by its name, with no zip64. The upload reads the app first (`application.one`), then sends the zip as a multipart form with the app's id and its `dropBuildPath`, when it has one, so the owner's build path stays: Dokploy otherwise sets it to empty. It prints `<name> (<id>) on instance <name>: sent 3 files, 1200 bytes, as a zip of 640 bytes; Dokploy queued a deployment; to follow it: arthur dokploy status` (`sent site.zip as it is, 640 bytes` for a ready zip). Dokploy: `POST /api/application.dropDeployment` ([application](https://docs.dokploy.com/docs/api/application), "Application drop Deployment"). A folder goes as it is, `.env` or `.git` in it included: give the folder that holds what the app needs.
- `--replace-source`: an upload makes the app deploy from `drop`. An app that deploys from another source (`github`, `git`, `docker`, ...) and has deployments is refused after the read, before anything is sent: `Live API (kXx3...) on instance (unnamed) deploys from github and has deployments; an upload makes it deploy from drop: add --replace-source for that; nothing was sent`. With `--replace-source` it is switched. An app without deployments is uploaded to without it, since Dokploy gives a new app the source `github`.
- `deploy [<app>]`: starts a deployment of the app from the source it has: `app <id> on instance <name>: Dokploy queued a deployment; to follow it: arthur dokploy status`. Dokploy: `POST /api/application.deploy` with `{ "applicationId": "<app>" }` ([application](https://docs.dokploy.com/docs/api/application), "Application deploy").

A write that got no answer within `timeoutSeconds`, or no answer at all, may still have been made: `arthur dokploy status` shows whether a deployment started before trying again. `dropDeployment` unzips the upload before it answers, so a large one needs a `timeoutSeconds` above the default 60.

## A new app

Only when the owner asks, as for an upload or a deploy: each changes what his server runs. The key stays in Arthur's environment, so a new app never needs it copied into a script.

- `create <name> --dokploy-project <name> [--environment <name>]`: a new application named `<name>` in the Dokploy project `--dokploy-project` names (as `apps` prints it), in its environment `--environment` names, else in the project's default one (Dokploy's `production`). `--dokploy-project` and not `--project`, which names one of Arthur's projects. The instance is `--instance`, else the `--project` project's, else the only one. It reads `project.all`, then sends `POST /api/application.create` with `{ "name", "environmentId" }` ([application](https://docs.dokploy.com/docs/api/application), "Application create"), and prints `created Shop admin (kXx3new4) in project Shop, environment production on instance (unnamed); to set it up: arthur dokploy setup kXx3new4`. Dokploy gives a new app the source `github` and the build type `nixpacks`; an upload switches it to `drop` without `--replace-source`, as it has no deployments.
- `setup <app>`, with at least one of its flags: `--dockerfile <path>` and `--context <path>` set the build type `dockerfile` with that Dockerfile and build context (`POST /api/application.saveBuildType`; the one left out stays as the app has it, a Dockerfile the app lacks is Dokploy's default `Dockerfile`, and the stage and the Heroku and Railpack versions go back as they are); `--domain <host> --port <n>`, always together, adds the domain on https with a Let's Encrypt certificate, routed to the container's port `<n>` (`POST /api/domain.create`, [domain](https://docs.dokploy.com/docs/api/domain)); `--volume <name>:<path>` mounts the named Docker volume `<name>` at `<path>` in the container (`POST /api/mounts.create`, [mounts](https://docs.dokploy.com/docs/api/mounts)). Each part already in place is left as it is and said so, so a call may be run again: a `dockerfile` build with the same Dockerfile and context, a domain with that host in any case (whatever its port), a volume of that name at that path. It prints the app's heading, one line per part (`build type: dockerfile Dockerfile, context .: set`, `domain https://shop.example/ to port 3000: added, its certificate from Let's Encrypt`, `volume uploads at /app/uploads: added`, or `...: already set`), then, when it wrote the build type or a volume, `a deploy applies the build type and the volume: arthur dokploy deploy <app>`; Dokploy routes a new domain at once.
- With `--domain`, Dokploy is asked first whether the host resolves to the server the app runs on (`POST /api/domain.validateDomain`): when it says no, a warning on stderr names the host and Dokploy's reason, `warning: shop.example does not resolve to the server of Shop web (kXx3shopWeb01) on instance (unnamed): Domain resolves to 198.51.100.7 but should point to 203.0.113.10`, and the domain is still added: Let's Encrypt issues its certificate once the DNS points there.
- `env <app> names`: the names of the app's environment variables, one per line in name order under its heading, or `: no variables`; never a value. Comments, blank lines and the lines of a value over several lines are no names.
- `env <app> set <NAME> <value>`: sets one variable; every other line of the env (comments, blank lines, other variables) stays as it is. A line that sets `<NAME>` is replaced (`<NAME> replaced, on 1 line`), else `<NAME>=<value>` is added at the end (`<NAME> added`); the value is written as given, else in single, else in double quotes, the first form a dotenv parser (Node's, as Dokploy reads the env with dotenv) reads back as the value given. The build args, build secrets and `createEnvFile` go back as the app has them (`POST /api/application.saveEnvironment`). The command never prints the value, in its output or an error: a value Dokploy's error text quotes, the value sent or a value of the env, the build args or the build secrets, shows as `[hidden]`. A value equal to the one set prints `<NAME> already holds that value; nothing was sent`. The value may be empty or start with `-`. It is a word of the command line, so the shell's history and the session that ran the command hold it, as the owner's message that gave it does. A deploy applies it: the line ends with the `arthur dokploy deploy` call.

## From Git

Only when the owner asks, as for the writes above: from then on, each push to the branch changes what his server runs.

- `source <app> --repo <owner>/<name> --branch <branch>`: the app deploys from the GitHub repository `<owner>/<name>`, branch `<branch>`, through a GitHub app of Dokploy (Settings, Git providers), with auto-deploy on, so a push to that branch deploys it: GitHub sends the push to Dokploy's own webhook, `<panel>/api/deploy/github`, which deploys each app with that repository, branch and GitHub app whose trigger is `push` and whose auto-deploy is on. The GitHub app is the one `--github <name>` names, by its name in the panel, else the only one the token's user may use. It reads the app (`application.one`), the GitHub apps (`GET /api/github.githubProviders`), the repositories that GitHub app's installation sees (`GET /api/github.getGithubRepositories?githubId=<id>`) and the repository's branches (`GET /api/github.getGithubBranches?repo=<name>&owner=<owner>&githubId=<id>`), then sends `POST /api/application.saveGithubProvider` with `applicationId`, `githubId`, `owner`, `repository`, `branch`, `buildPath`, `triggerType: "push"`, and the app's own `watchPaths` (else `[]`) and `enableSubmodules`, and then `POST /api/application.update` with `{ "applicationId", "autoDeploy": true }`, only when the app's auto-deploy is not on already. The owner and the name may be given in any case; they are saved as GitHub writes them, since the webhook compares them so. It prints `Fresh (kXx3fresh03) on instance (unnamed): source github acme/web-shop, branch main, build path /, GitHub app acme: set`, then `a push to main deploys it; the first deploy: arthur dokploy deploy kXx3fresh03`. An app that has this source already, with the trigger `push` and auto-deploy on, prints the first line ending `: already set`, and nothing is sent.
- `--build-path <path>`: the folder of the repository the build runs in, from `/`, default `/`; the Dockerfile and context `setup` sets are read inside it. It is saved whether given or not: an app built from another folder goes back to `/` without it.
- `--replace-source`: an app with deployments that deploys from another source (`drop`, `docker`, ...), or from another repository, branch or GitHub app, is refused after the reads, before anything is sent: `Drop (kXx3drop04) on instance (unnamed) deploys from drop and has deployments; this makes it deploy from github acme/web-shop, branch main: add --replace-source for that; nothing was changed`. With it the source is switched. An app without deployments is connected without it, as is one whose repository and branch stay and whose build path or auto-deploy changes.

A push reaches Dokploy only when its panel is reachable from GitHub: what the owner sets up once, the GitHub app among it, is in [`../dokploy.md`](../dokploy.md).

## A database

Only when the owner asks, as for the writes above: a database holds his data and runs on his server.

- `postgres create <app> <name>`: a Postgres named `<name>` beside the app, in the app's own environment and on its server, its URL in the app's env, then deployed. It reads the app (`application.one`) and its environment (`GET /api/environment.one?environmentId=<id>`). When that environment has no Postgres named `<name>`, it sends `POST /api/postgres.create` with `{ "name", "environmentId", "serverId" (when the app has one), "dockerImage": "postgres:<n>", "databaseName": "postgres", "databaseUser": "postgres", "databasePassword" }`; Dokploy mounts the data volume `<appName>-data` itself. The password is 64 hex characters Arthur makes for this call alone (within Dokploy's own rule for a database password); it keeps it nowhere and never prints it.
- The app's env gets `DATABASE_URL=postgresql://postgres:<password>@<appName>:5432/postgres`, the internal URL as Dokploy's panel builds it, `<appName>` the database's (`postgres-...`), the user and password percent-encoded; it is set as `env set` sets a variable, every other line kept (`POST /api/application.saveEnvironment`). Then `POST /api/postgres.deploy`, which answers once the image is pulled and the database runs. It prints `created Postgres db (pgX1) beside Shop web (kXx3shopWeb01) on instance (unnamed), internal host postgres-parse-online-pixel-k7m2q1:5432, image postgres:18` before it sets the env, then the env's line, `Shop web (...): DATABASE_URL added; every other line kept; a deploy applies it: arthur dokploy deploy kXx3shopWeb01`, then `Postgres db (pgX1): deployed; to see it: arthur dokploy postgres status pgX1`. The URL and the password are never in the output, and show as `[hidden]` in Dokploy's error text.
- `--version <n>`: the image `postgres:<n>`, 1 to 99, default 18, Dokploy's own default. `--env <NAME>`: the variable that gets the URL, default `DATABASE_URL`.
- Each part already in place is left as it is, so a call may be run again: a Postgres of that name in the app's environment is kept (`Postgres db (pgX1) beside ...: already there`), and its URL is built from what Dokploy holds of it (`GET /api/postgres.one`), its own user and database; an env that holds that URL is not sent again (`DATABASE_URL already holds that value; nothing was sent`); a database deployed already is not deployed again (`Postgres db (pgX1) is done: not deployed again`), one still `idle` is.
- The env is set before the deploy, so a deploy that gives no answer within `timeoutSeconds` (the first pull of an image may take longer than the default 60) still leaves the app connected; the error names `arthur dokploy postgres status <postgres>` to see whether the database runs.
- `postgres status <postgres>`: `Postgres db (pgX1) on instance (unnamed): done`, then its image, internal host `<appName>:5432`, database and user, each volume as `volume <name> at <path>` (or `no volume`), and each backup as `backup <id>: <schedule> to <destination>, keeps the latest 7, enabled` (or `no backups`). Never its password or URL. Dokploy: `GET /api/postgres.one?postgresId=<postgres>`. The instance is picked as for an app with an id: `--instance`, else the `--project` project's, else the only one.
- `postgres backup <postgres> --destination <name> --schedule "<cron>" [--keep <n>]`: Dokploy backs the database up to the S3 destination named `<name>` (Dokploy's panel, Settings, Destinations) on the cron schedule, five fields, minute, hour, day of month, month and day of week (`"0 3 * * *"`: each day at 03:00), keeping the latest `<n>` backups there, 1 to 9999, else every one. It reads the database (`postgres.one`) and the destinations (`GET /api/destination.all`, read for their names and ids only: the answer holds their S3 keys, which are never printed), then sends `POST /api/backup.create` with `{ "postgresId", "destinationId", "schedule", "keepLatestCount" (with `--keep`), "enabled": true, "prefix": "/", "database": <its database>, "databaseType": "postgres", "backupType": "database" }`; Dokploy schedules only a backup that is enabled. `backup.create` answers nothing, so it reads `postgres.one` again and prints the backup Dokploy lists now: `Postgres db (pgX1) on instance (unnamed): added backup bk3: 0 3 * * * to s3-main, keeps the latest 7, enabled; to see it: arthur dokploy postgres status pgX1`. A backup of that destination and schedule that keeps as many and is enabled is left as it is: `Postgres db (pgX1) on instance (unnamed): backup bk3: 0 3 * * * to s3-main, keeps the latest 7, enabled: already set; nothing was sent`. The instance is picked as for `postgres status`. Restoring a backup is done in Dokploy's panel.

Control characters in Dokploy's text are dropped before it is printed; a field a server leaves out prints `unknown`.

## Which app, on which instance

- Without `<app>`: the application of the project's `dokploy.project(...)`, the project `--project` names, else the main one, on the instance it names, else the unnamed one. `--instance` may be given only when it names that same instance.
- With `<app>`, an application id (1 to 64 letters, digits, `_` and `-`, as `apps` prints it): on the instance `--instance` names; without `--instance`, on the instance of the `--project` project's `dokploy.project(...)`; else on the only instance.
- `--instance` takes an instance's name; the unnamed instance has none, so it is reached through a project that names no instance, or as the only instance.
- `apps` reads every instance unless `--instance` names one.

## Refusals

Each comes before any request, exits 1, and ends `nothing was asked of Dokploy`:

- `--instance <name>` that is no instance of dokploy: `--instance acme is not an instance of dokploy; its instances: (unnamed), client`;
- several instances and a call that names none (`<app>` given without `--instance`, and no `--project` whose `dokploy.project(...)` gives an instance): `dokploy has 2 instances ((unnamed), client) and the call names none: add --instance <name>, or --project <name> of a project with dokploy.project(...)`;
- without `<app>`, an `--instance` other than the one the project's piece names: `--instance client is not instance (unnamed), which project shop's dokploy.project(...) names`;
- for `upload`, the path, named first (`dist: ...`): one that is missing or cannot be read, `cannot be read (ENOENT)`; a symlink, `is a symlink; give the path it points to`, and a special file, `is no file or folder`; a folder without any file, `is a folder without any file`; a symlink or a special file inside the folder, by its path there, never followed, `assets/logo.png is a symlink, not a regular file`; more files than a zip holds, `holds 65536 files, more than the 65535 a zip holds`; files that come to more than 4 GiB as a zip, each counted as it is with its headers, `its files come to 4294967400 bytes as a zip, more than the 4 GiB a zip without zip64 holds`;
- for `setup`, `--port 0 is not a port: 1 to 65535`, and `--volume data is not <name>:<path>: a name of letters, digits, _, . and -, then a path from /`;
- for `env set`, `A-B is not a variable name: a letter or _, then letters, digits and _`;
- for `source`, `--repo acme is not <owner>/<name>: an owner of letters, digits and -, a name of letters, digits, ., _ and -`; `--branch feat branch is not a branch Dokploy takes: letters, digits, ., _, -, / and #`, Dokploy's own rule; `--build-path apps/web is not a folder of the repository: a path from /, without a .. part`;
- for `postgres create`, `--version 100 is not a Postgres major version: 1 to 99`, and `--env A-B is not a variable name: a letter or _, then letters, digits and _`; for `postgres status` and `postgres backup`, `the Postgres is not a Dokploy id: 1 to 64 letters, digits, _ and -`;
- for `postgres backup`, `--schedule 0 3 * * * * is not a cron schedule of five fields, minute, hour, day of month, month and day of week, as "0 3 * * *"` (each field of digits, letters, `*`, `,`, `/`, `?`, `#` and `-`, one space between two), and `--keep 0 is not how many backups to keep: 1 to 9999`.

After the read and before any write, ending `nothing was created`, `nothing was changed` or `nothing was sent`:

- for `create`, a project the instance does not have, `instance (unnamed) has no project Shp; its projects: Shop, Archive`; an environment it does not have, `project Shop has no environment preview; its environments: production, staging`; no `--environment` and no default one, `project Random has no default environment: add --environment <name>; its environments: none`; a name the environment's apps have, `project Shop, environment production already has an app named Shop web (kXx3shopWeb01)`;
- for `setup --volume`, a path another mount of the app holds, `Shop API (kXx3shopApi02) on instance (unnamed) already mounts bind /srv/data at /var/data`;
- for `env set`, a value no line reads back, `... the value of A cannot be written as a line that reads back as given, as it is or in either quotes; set it in Dokploy's panel`; a name set over several lines or inside another value, so that a line set here would change another variable, `... the env holds CERT over several lines or inside another value, so a line set here would change another; set it in Dokploy's panel`;
- for `source`, ending `nothing was changed`: no GitHub app the token's user may use, `instance (unnamed) has no GitHub app the token's user may use: the owner adds one in Dokploy's panel, Settings, Git providers, and installs it on acme/web-shop`; several and no `--github`, `instance (unnamed) has 2 GitHub apps: add --github <name>; its GitHub apps: acme, acme-two`; a `--github` no GitHub app has, `instance (unnamed) has no GitHub app acme-three; its GitHub apps: acme, acme-two`; a GitHub app Dokploy answers without an id, `instance (unnamed): GitHub app acme has no Dokploy id`; a repository the GitHub app does not see, `GitHub app acme cannot see acme/shop: install the GitHub app on it (GitHub, Settings, GitHub Apps, Configure), then run this again`; a branch the repository does not have, `acme/web-shop has no branch develop`; another source with deployments and no `--replace-source`, as above;
- for `postgres create`, ending `nothing was changed`, before any database is made: an app whose env sets the variable already, to anything but this database's URL, so the owner's value is never lost, `Shop web (kXx3shopWeb01) on instance (unnamed) already sets DATABASE_URL to another value: give --env <NAME> for another name`; an app cut off from `dokploy-network` (detached from it, or its own swarm networks without it), which could not reach the database by its internal name, `Shop web (kXx3shopWeb01) on instance (unnamed) is not on dokploy-network, so it cannot reach a database by its internal name: attach it to dokploy-network in Dokploy's panel`;
- for `postgres backup`, ending `nothing was changed`: a destination the instance does not have, `instance (unnamed) has no destination s3-gone; its destinations: s3-main, s3-cold (Dokploy's panel, Settings, Destinations)`; two of that name, `instance (unnamed) has 2 destinations named s3-main: rename one in Dokploy's panel`; one Dokploy answers without an id, `instance (unnamed): destination s3-main has no Dokploy id`; a database Dokploy answers without its database name, `instance (unnamed): Postgres pgX1: Dokploy's answer lacks its database`; a backup of that destination and schedule that keeps another count or is disabled, `Postgres db (pgX1) on instance (unnamed) already has backup bk1: 0 3 * * * to s3-main, keeps the latest 7, enabled: change it in Dokploy's panel`.

A part of `setup` or `postgres create` that failed leaves the parts before it made: run it again, and what is in place is left as it is.

Wrong usage (an unknown verb, a word too many or too few, `upload` without a path, `create` without `--dokploy-project`, `setup` without any of its flags, `--domain` without `--port` or the other way round, `env` with neither `names` nor `set <NAME> <value>`, `source` without `--repo` or `--branch`, `postgres` with neither `create <app> <name>`, `status <postgres>` nor `backup <postgres>`, `postgres backup` without `--destination` or `--schedule`, a flag given twice or to another verb (`--version` or `--env` to `postgres status` or `postgres backup`, `--keep` to `postgres create`), a flag without its value or one starting with `-` (`--keep -1`), another flag) prints the usage line and exits 2.

## Errors from Dokploy

One line, exit 1, naming the instance; the token is never in it (`[token]` where Dokploy echoed it):

- 401: `instance client: 401: the token in ARTHUR_DOKPLOY_CLIENT_TOKEN was refused: Unauthorized`;
- 403: `instance client: 403: the token's user may not read app kXx3...: <Dokploy's message>`, `may not change` for a write;
- 404: `instance client: 404: app kXx3... not found` (the id may be on another instance);
- any other status, 400 and 500 among them: `<status> for <what>: <Dokploy's message>`;
- no answer within `timeoutSeconds`: `no answer in 60 s from <url> for <what>`;
- no server: `cannot reach <url> for <what> (ECONNREFUSED)`;
- a redirect: `<url> answered <what> with a redirect, which is not followed: the token goes only to the configured url`;
- an answer that is not JSON: `the answer for <what> is not JSON`; a deploy's answer is empty, as Dokploy sends it.

The plugin's options and its refusals at load are in [`../dokploy.md`](../dokploy.md).
