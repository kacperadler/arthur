# arthur coordinator

Usage: `arthur coordinator stop`, `arthur coordinator context`. Comes with the `orchestration` plugin, which every config holds.

## The coordinator's process

The coordinator is one interactive agent (`core.agent.command`, `omp`) in its own tmux session, `coordinator.tmux.session` (default `arthur`) on its own tmux server, `coordinator.tmux.socket` (default `arthur`: a name, as `tmux -L arthur`; one with a `/` is a socket path, as `tmux -S <path>`). `arthur run` keeps it running from its `start` until its `stop`:

1. At `arthur run`'s start, a stop mark left by `arthur coordinator stop` is lifted. A session already running under that name (left by an `arthur run` that crashed) is kept, not started twice.
2. Every 500 ms it looks at the session. When the session is gone, or its agent exited and the pane stayed (a `remain-on-exit` in the human's `~/.tmux.conf`; the session is then killed), the coordinator has ended, for whatever reason: the agent quit or crashed, or someone killed the session. It is started again `coordinator.restartDelaySeconds` (default 5) after that, so a coordinator that crashes at once does not start more often than once per delay.
3. A start first waits, up to `coordinator.exitWaitSeconds` (default 60), until the agent of the previous start has exited, so two never refresh the agent's credential at once (a refresh token is used once; the loser's login is lost). The previous agent is the pid `<home>/orchestration/coordinator.pid` names, with its start time from `ps`, so a pid reused by another process does not count, after a reboot for example.
4. Then `tmux new-session -d -s <session> -c <the folder arthur run runs in> -e ARTHUR_ORCHESTRATION_FOLDER=<home>/orchestration -e ARTHUR_ORCHESTRATION_CONTEXT=<the context command>` starts `<agent> [--continue] --auto-approve [--model <coordinator.model>] [--thinking <coordinator.thinking>] [--smol <roles.quick.model>] -e <@arthur/core/env-guard> -e <the inbox extension> -e <the context extension>`: the last conversation goes on (a new one when there is none; without `--continue`, a fresh conversation, once after `coordinator.restart` with `fresh: true`, below), nobody is there to approve tool calls, the env guard refuses a tool call naming a secrets file as it does in every job (see `arthur spawn --help`), the inbox extension (`packages/orchestration/src/inbox-extension.ts`) hands the coordinator its messages, and the context extension (`packages/orchestration/src/context-extension.ts`) gives it its role and context before every turn (both below). The context command is a JSON list: the `node` that runs `arthur run`, the core's CLI, `coordinator`, `context`.
   After its own three, the coordinator loads each OMP extension another plugin answers to `collect("coordinator.extension")` with `{ file, env }` (the session plugin's handoff and turn extensions, `packages/session/docs/session.md`): `-e <file>`, and each of its `env` variables as one more `-e <NAME>=<value>` of `tmux new-session`. They are collected once, at `arthur run`'s start. An answer that is not an absolute path to an existing file with `env` variables named `ARTHUR_*` holding text, or a provider that throws, is left out: `orchestration: the coordinator.extension of <plugin> is left out: <why>`.
5. At `arthur run`'s `stop` the session is killed.
6. Another plugin ends the coordinator through `call("coordinator.restart", { fresh })` (the session plugin's `/restart` and fresh start, `arthur restart --help`): its session is killed, so it is started again as in step 2; with `fresh: true` the mark `<home>/orchestration/fresh` is left first, and the next start is made without `--continue` and removes it. Anything but `{ fresh: true | false }` is refused: `coordinator.restart: expected { fresh: true | false }, got <value>`. It does not count running jobs: that is the caller's rule.

Lines it prints in `arthur run`'s output:

- `orchestration: coordinator started: <agent> (pid <pid>) in tmux session <session>`, with `, a fresh conversation` after the mark of step 6.
- `orchestration: the coordinator ended; starting it again in <n> s`, or, after `arthur coordinator stop`, `orchestration: the coordinator ended; arthur coordinator stop asked, so it stays stopped until arthur run starts again`.
- `orchestration: the previous <agent> (pid <pid>) exited after <s> s`, when a start had to wait.
- `orchestration: coordinator start refused: the previous <agent> (pid <pid>) is still running <s> s later; trying again in <n> s`: the start is not made, and is tried again after the delay, waiting again, until the previous agent is gone.
- `orchestration: coordinator start failed: tmux new-session: <tmux's last line>; trying again in <n> s`, for tmux missing or refusing (the session name taken by another tmux server on that socket, for example).

Without tmux there is no coordinator, so the plugin gives `arthur doctor` one critical requirement, `orchestration tmux`: `tmux -V` runs, or `missing: tmux not found on PATH` (or `tmux -V: <its error>`), whose fix is `sudo apt-get install -y tmux`. It refuses the start of `arthur run` before any plugin's start (`arthur doctor --help`).

## The coordinator's inbox

Every message for the coordinator becomes a turn of its conversation, and every turn's last reply goes back out:

- What reaches it: `message-received` `{ channel, text }`, the owner writing from a channel (an event without both as non-empty text is not queued: `orchestration: message-received (event <n>) ignored: expected { channel, text }, both non-empty text`); `coordinator-message` `{ text }`, from a plugin such as schedule (likewise checked); and `job-ended`, the wake: the state the run ended in, `Job <id> ended its run: <state> (<reason>).`, or for a run blocked on the owner `Job <id> ended its run blocked on the owner; its question, also sent as a notice: <question>` (see "Jobs blocked on the owner"), then `Project: <project>.` when it is not the main one, the first 15 lines of the job's final message, and each line a plugin answers to `collect("coordinator.wake", <the job-ended data>)`, the procedure of its kind.
- Each one is a file `<home>/orchestration/inbox/queued/<event number>-<its time in ms>`, written by every process that gets the event (a command's and `arthur run`'s); one already in `queued/`, `turn/` or `answered/` is not written again, so an event delivered twice is one message. The time keeps a log cut by hand, whose numbers start again, from matching an old event's file, so a new message of an old number is queued. The messages go in the order of their numbers.
- While the coordinator is idle, everything queued goes as one turn, in order, once the queue has not grown for 1 s; a turn holding no owner message is attributed to the agent, not the user.
- During a turn, the owner's messages join it: after the next tool call, together as one message delivered at omp's next step boundary without cutting the running tool batch (`deliverAs: "aside"`); after the last tool call, when the turn would end, the turn is resumed with them and told that its reply above was not sent, so it writes one reply that answers everything (omp's `session_stop` continuation, at most 8 in a turn; past that a message is the next turn). A job's end and a plugin's message never join a turn; they wait for the next one.
- Each message is one paragraph, marked: `[via <channel>]` or `[Arthur]`, then `sent during this turn`, `sent during this turn, after your last tool call`, `sent before a restart; no reply to it was sent`, or `sent before; its turn ended without a reply`. A turn with an `[Arthur]` message ends with the line `The lines marked [Arthur] come from Arthur (a job's end, a schedule), not from the owner.`
- A handed message moves to `inbox/turn/`. When the turn ends with a reply, its text goes to `<home>/orchestration/outbox/` as `{ text, answers: [the files it answers, `<event number>-<time>`], channels: [the channels of the owner messages it answers] }`, and only then do the turn's messages move to `inbox/answered/`. `arthur run` emits each reply as `coordinator-replied` `{ text, answers: [event numbers], channels }` within 500 ms, then moves it to `outbox/sent/`. A turn that ends in an error, aborted, or on a tool call answers nothing: its messages go again, marked.
- The messages of a turn that ended without a reply go again at the next tick the first time; after the second such turn in a row they wait 5 s, and each time after twice as long, at most 5 min. A new owner message (`message-received`) ends the wait: the waiting messages and the queued ones go with it at the next tick; a job's end or a plugin's message that comes meanwhile waits with them. The third such turn in a row emits one `notice` `{ text: "the coordinator's last 3 turns ended without a reply (<stop reason>: <error>); their messages go again in 10 s, then after twice as long each time, at most 5 min" }`, the error's credentials redacted as in the session plugin's turn-failed notice (`packages/session/docs/session.md`): the value of every environment variable whose name holds `KEY`, `TOKEN`, `SECRET`, `PASSWORD`, `CREDENTIAL` or `AUTH` (8 characters or more), a `Bearer` token, a key with a vendor's prefix (`sk-`, `xoxb-`, `ghp_`, ...), and any run of 20 or more letters, digits, `_` and `-` that mixes letters and digits become `[redacted]`. A turn that ends with a reply ends the wait and the count.
- A hand-over omp refuses at once is tried again every 500 ms. One omp accepts and then fails (its error shows in the coordinator's pane, `No API key found` for example) starts no turn: when omp has been idle for 30 s since the hand-over with no `agent_start`, its messages go again, with their marks, at the next tick. omp is busy through its compaction before a prompt, however long, so that never counts; a `/compact` typed in the pane is idle, and one longer than 30 s gets a hand-over made meanwhile delivered twice. Both kinds count in a row until a turn starts; the third emits one `notice` `{ text: "the coordinator's inbox could not hand <n> message(s) to the agent 3 times in a row (<error, or no turn started within 30 s>); it keeps trying" }`.
- A turn whose `agent_end` says it goes on (`willContinue`) and then starts none, as after omp's compaction of a turn that ended, ends with that `agent_end` once omp has been idle for 30 s: its reply is sent as above, and the next messages go.
- At a restart of the coordinator, a message left in `inbox/turn/` that a reply in `outbox/` or `outbox/sent/` answers by its file's name moves to `answered/`; every other one goes again as the first turn, marked `sent before a restart`. Files in `answered/` and `outbox/sent/` older than 7 days are deleted then.
- The footer of the coordinator's screen shows `arthur · <n> <state>, <n> <state>: <short ids>` while jobs are in a run (working, idle, or held `blocked`), counted by state, `blocked` first, then `working` and `idle`, the ids in that order (`arthur · 1 blocked, 2 working: 0000000e, 0000000f, 0000000a`); empty when none is. The plugin writes it to `<home>/orchestration/footer` at each `job-started`, `job-state` and `job-ended`.
- The extension acts only in the coordinator's own session, one with a UI: never in a `task` subagent.

## The coordinator's context

Before every turn, the context extension runs the context command in the coordinator's folder (the one `arthur run` runs in, which holds `arthur.config.ts`) and adds what it prints, as one part, to the end of the agent's system prompt: what changed since the last turn (a ticket, a new hour, a plugin's line) is there in the next. It acts only in the coordinator's own session, one with a UI, never in a `task` subagent. `arthur coordinator context` prints the same text, so the owner can read what the coordinator reads:

1. The coordinator's role, read as every role is (`arthur roles --help`): the role file `packages/orchestration/roles/coordinator.md`, the main project's override `.agents/arthur/roles/coordinator.md`, and its criteria files `styleguide` and `autopilot` (see "Autopilot"). `arthur roles` lists it, with no kind.
2. `## Vision of <project> (<path>)` and the file, for each project in the list's order: its vision, `spec/vision.md` unless its `prompts.vision` says otherwise.
3. `## Warnings`, when there is one, a line each: `- criteria file <path> is missing; the coordinator goes without it`, `- criteria file <path> is empty; nothing added`, `- project <name> has no vision: <path> is missing|empty|a symlink|not a file; the coordinator goes without it` (never read through a symlink), `- project <name>: its vision was not read: <error>` (a folder that is no Git repository, a `prompts` path refused).
4. `## Board of <project>` and its digest, for each project: every open ticket, the 10 newest merged, and one line counting the rest (`arthur ticket --help`). A board that cannot be read costs that board only: `the board was not read: <error's first line>`. Without the projects plugin the one section is `## Board` and says why there is no board.
5. `## Jobs not ended`, only when there is one: every job of every project whose state is not `ended`, grouped by state, `blocked` first, then `working`, `idle`, and a state written by hand by its name, each group headed `<state>:` and in `arthur jobs`' order (the newest spawn first); one line each, `- <id>, for <h>h<mm>m: <reason>`, the time since it took its state (`since an unknown time` when its record has none), `, project <name>` after the id for a job not of the main project, no reason when it has none. It is read from the job records at each turn, so a blocked job continued before the turn shows as working.
6. `## Time`: `<HH:MM> on <day> <YYYY-MM-DD> (<core.timeZone>), night: within the owner's quiet hours.` from `host.clock`, or `..., day: outside the owner's quiet hours.`; night is `core.quietHours`, across midnight when `from` is the later time (22:00 to 07:30: 23:30 and 03:00 are night, 07:30 is day); without quiet hours it is always day.
7. What each plugin answers to `collect("coordinator.context")`, in setup order, under `## <plugin>`: text (the projects plugin's block of project lines, the session plugin's `Restart:` line of its restart guard, later manage's retro due). Undefined or blank text adds nothing. A provider that throws costs its own section only: `coordinator.context failed: <error's first line>`; one that answers anything but text: `coordinator.context answered <type>, not text`.

Parts are separated by a blank line. When the command fails (exit not 0, or 60 s without an end), the turn still goes: the system prompt gets the shipped role file and `## Context` saying `Arthur could not build your context this turn (the board, the visions, the time): <what the command printed on stderr>`, and to say so in the reply. A symlinked override or criteria file of the main project fails it so: `<path> is a symlink; refused, the roles read a project's file only as a plain file`.

`arthur coordinator context` exits 0 with the text, 1 when it cannot be built (`arthur coordinator: <error>`).

## Jobs blocked on the owner

A job whose run ends with `Blocked: user <question>` as the first line of its final message is `blocked` on `user: <question>` (`arthur jobs --help`). At that `job-state` the plugin emits one `notice` `{ text: "<id> asks: <question>" }`, which every channel sends, at once, also in quiet hours, when a channel sends it without a notification (the channel's rule). A text longer than one message (4096 characters, Telegram's limit) is cut to 4096, ending `… (cut; /jobs shows the whole question of job <short id>)`, never through a character of two UTF-16 units. A block on a dependency (`Blocked: on …`, a plugin's hold) sends none.

One notice per block: every process that loads the plugin gets the event (`arthur run`, and a command such as `arthur stop` that moves the job), and `arthur run` gets it again after a crash, so the first to create `<home>/orchestration/asked/<event number>-<its time in ms>` sends it and the others none (the time, so a log cut by hand, whose numbers start again, never matches an old mark); files there older than 7 days are deleted at the next block. A later block of the same job, after `arthur continue`, is a new event and a new notice. `/jobs` on a channel shows each job's state, reason and for how long (`arthur jobs --help`).

## arthur coordinator stop

Ends the coordinator's session and keeps it stopped until `arthur run` starts again (a restart of its service, for example). It writes the stop mark `<home>/orchestration/stopped` first, then kills the session, and prints `arthur coordinator stop: tmux session <session> (socket <socket>) ended; it stays stopped until arthur run starts again`, or `... was not running; ...` when no session ran (the mark still keeps it from being started).

Refused, exit code 1, while any job of any project is in a run (`working`, `idle`, or held `blocked`, as `arthur stopall` counts them): the coordinator is who hears a job's end, so nobody would. `arthur coordinator stop: refused: <n> jobs running: <id>, <id>; the coordinator is who hears their end; stop them first (arthur stop <id>, or arthur stopall)`. There is no force mode.

Wrong usage (no argument, another one, more than one) prints `usage: arthur coordinator stop|context` and exits 2.

## Options

In `orchestration({ ... })` in `arthur.config.ts`, every key optional; an unknown key or a wrong value refuses the start, naming its path:

- `maxAgents`: a whole number of at least 1, default 3.
- `coordinator`: `model` (a non-empty string), `thinking` (one of `off`, `minimal`, `low`, `medium`, `high`, `xhigh`, `max`, `auto`), `tmux: { session, socket }` (the session: letters, digits, `_` and `-`, since tmux reads `:` and `.` in a target; the socket: a non-empty string), `exitWaitSeconds` (a whole number of at least 0), `restartDelaySeconds` (a whole number of at least 1).
- `roles`: one entry per role, its name lowercase letters, digits and dashes, each `{ model, thinking }`: `model` a model name or a non-empty list of them, `thinking` as above. The entry `quick` is not a role: `{ model }` only, a model name. An entry `coordinator` is refused: the coordinator's are `coordinator.model` and `coordinator.thinking`, which `arthur roles` shows for the role `coordinator`.
- `plan: { budgetUsd }`: the budget of a plan job, an amount in USD, 0 or more, default 5 (`arthur plan --help`).
- `autopilot: { budgetUsd, budgetMaxUsd }`: amounts in USD, 0 or more: the budget a pre-approved ticket's worker gets when `--budget` and the ticket's own `budget` are left out, default 1, and the most it may get, default 3 (see "Autopilot"). A `budgetUsd` above `budgetMaxUsd`, either left out at its default, refuses the start: `autopilot.budgetUsd: expected at most autopilot.budgetMaxUsd (<cap>), got <budget>`.
- `morningReport: { at }`: `"HH:MM"`, 00:00 to 23:59.

`morningReport` is checked here for its shape; the entry that reads it says what it does.

## Autopilot

`arthur ticket status <id> planned --autopilot [--budget <usd>]` sets a ticket `planned` without the owner's word, pre-approved by policy, so a small bug or cleanup that an audit or a finding brought runs overnight. The core hands it to this plugin (`ticket.autopilot`), which checks every rule against the ticket's `ticket.md` in the project's folder (the working tree, so commit it after), and refuses with all the rules it breaks in one line, exit code 1, the ticket left as it was: `arthur ticket: <id>: not pre-approved: <rule>; <rule>`:

- The ticket is in `planning`: `it is <status>; autopilot pre-approves a ticket in planning`. So a second `--autopilot` on a pre-approved ticket adds no second record, also when both run at once: each takes a lock per ticket, `autopilot-<id>.lock` in the plugin's folder, around the check, the record and the move, and the second waits for the first.
- It came from a finding or an audit: a line `- YYYY-MM-DD: Source: F<n> of <id>` under its Decisions, where ticket `<id>` is on a board and its `findings.md` has the heading `## F<n>. `, or `- YYYY-MM-DD: Source: audit spec/quality/<file>.md`, a file of the ticket's project. Else: `it is not from a finding or an audit: ...`.
- Its kind, the `- Kind:` line under its Goal, is `bug` or `cleanup`: `its kind is <kind>; autopilot pre-approves only bug or cleanup` (`missing (- Kind: under its Goal)` when there is none).
- Its Scope names 1 to 3 files: each backticked path before the line `Out:` (the whole Scope without one), outside the template's guidance comments (`<!-- ... -->`), that has no space and has a `/` or ends in `.<ext>`, a line number after it (`a.ts:12`, `a.ts:40-52`) left off, each counted once; a backticked name such as `fixIt` or `arthur ticket` is no file. `its Scope names no file (a backticked path before Out:)`; `its Scope names <n> files, at most 3: <paths>`; a folder (one ending in `/`, or a folder in the project) or a pattern (`*`, `?`, `[`, `{`): `its Scope names a folder or a pattern, not one file: <paths>`.
- None of them is on delivery's always-review list. The plugin asks `call("delivery.alwaysReview", { project, paths })`; the answer is the list of those paths that are on it (the delivery plugin, roadmap entry 53, provides it). `on delivery's always-review list: <paths>`. Without delivery, so with nobody to ask, it refuses rather than passes: `the always-review list was not asked (plugin orchestration: call("delivery.alwaysReview"): no plugin provides it); autopilot refuses rather than passes`; an answer that is not a list of paths: `delivery.alwaysReview answered no list of paths; autopilot refuses rather than passes`.
- Its budget, `--budget`, else the `budget` key of the ticket's JSON block (an amount in USD, which the findings plugin, roadmap entry 83, writes there), else `autopilot.budgetUsd` (default 1), is above 0 and at most `autopilot.budgetMaxUsd` (default 3): `budget $0; a pre-approved ticket needs a budget above 0 (--budget, the budget of its JSON block, or autopilot.budgetUsd)`; `budget $<n> is over the cap of $<cap> (autopilot.budgetMaxUsd)`; a `budget` that is no number, `budget "2"; ...`; with `--budget` left out, a JSON block that is not JSON: `its JSON block is not JSON (<error>); fix it by hand`.

When every rule holds, the line `- YYYY-MM-DD: Pre-approved by policy: <kind> from <source>, <n> Scope files, budget $<budget> of the $<cap> cap` (today in `core.timeZone`) goes last under its Decisions, written whole and renamed, and the ticket moves to `planned` as `arthur ticket status` moves it (`ticket-moved`, from this plugin). A move the board refuses (a guidance comment of the template left in `ticket.md`, for example) puts the `ticket.md` back as it was and prints the board's refusal. It prints `<id> planned: Pre-approved by policy: ...; spawn its worker with --budget <budget>`. A ticket not on the board: `<id> is not on the board`. Wrong usage, exit code 2: `--autopilot` with another status or more than one ticket (`--autopilot sets one ticket planned`), `--budget` without a value or with one that is not a number of 0 or more, given twice, or without `--autopilot`.

Pre-approval changes who approved the ticket and holds its worker's budget: a worker, or an `arthur continue` of one, on a ticket whose `ticket.md` at HEAD holds a `Pre-approved by policy` line under its Decisions is refused with a budget of 0 (no limit) or above that line's (the last one): `refused by orchestration: <id> is pre-approved by policy with a budget of $<n>; its worker gets at most that, above 0, not $<budget>: --budget <n>, or the owner's approval under its Decisions ("- YYYY-MM-DD: The owner approved ...")`. A Decisions line after it that says `the owner approved` or `approved by the owner` lifts it. Its review and merge go as for any planned ticket. The judgement it leaves to the coordinator, beyond these rules (which tickets to try, what the owner hears in the morning), is the project's criteria file `autopilot`, `<criteriaDir>/autopilot.md` (`.agents/arthur/criteria/autopilot.md` by default), which the coordinator's role reads; `packages/orchestration/criteria/autopilot.md` is a starting text to copy there. Without it the coordinator's context warns that it is missing.

## maxAgents and the models of each role

- `maxAgents` is the most jobs in a run at once (working, idle or held, as `arthur jobs` shows them), across every project and machine, every kind and every spawn, the human's `arthur spawn` and `arthur continue` included. A spawn or continue at the limit is refused before any worktree or record exists: `refused by orchestration: maxAgents is <n> and <count> jobs are in a run: <ids>; spawn again once one ends`. A job frees its slot the moment its state is `ended`, with no sweep. Two spawns at once, from one process or two, take turns from the checks to the record (the core's `<home>/spawn.lock`), so they never both take the last slot.
- Each role's `model` and `thinking` from `roles` go to the agent as `--model` and `--thinking`; `arthur spawn --model` and `--thinking` win over them. A role left out of `roles`, or without a `model` or `thinking`, uses the agent's own default for it. A `model` may be an ordered list: the models plugin (roadmap entry 82) picks the first available at each spawn (`arthur spawn --help`, "The model"); without it such a role's spawn is refused before any record exists: `a model list needs the models plugin`. Every role's model, as a list, is also `models.lists`, which the models plugin's `arthur doctor` lines read.
- `roles.quick.model` is omp's quick model for titles, compaction and scout subtasks: `--smol <model>` on every job, whatever its role, and on the coordinator. Left out, nothing is added. A job keeps it through `arthur continue`; `arthur roles` shows it per role.
- A thinking level that is not one of omp's (`off`, `minimal`, `low`, `medium`, `high`, `xhigh`, `max`, `auto`), from `--thinking`, is refused before any record exists: `refused by orchestration: thinking level "<value>" is not one of off, minimal, low, medium, high, xhigh, max, auto`. One in `roles` or `coordinator` refuses the start of `arthur run` instead.
