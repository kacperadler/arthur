# AR0323 - Check: which Arthur commands a job itself may run

The rule of this area: a job runs only the Arthur commands its role needs; merging, `--unreviewed`, spawning without a budget, stopping other jobs and sending to the owner stay with the coordinator.

What a job is, for this check: the agent the wrapper starts with `ARTHUR_JOB` set to the record's folder (`packages/core/src/wrapper.ts:129`), with `bash` among every kind's tools (`wrapper.ts:18-19`) and `--auto-approve`, as Arthur's Linux user, in a systemd scope `arthur-job-<id>.scope` when systemd is there (`packages/core/src/job-scope.ts:27`, `:63`) and bare otherwise. The CLI it can reach: `arthur <command>` loads `arthur.config.ts` from the working folder (`packages/core/src/cli.ts:64`), which the worktree lacks but the config folder has; reading and `cd` pass the worktree guard everywhere (AR0320), and the develop plugin's own prompt section tells a worker to do exactly that, `cd <checkout> && arthur plugin new …` (`packages/develop/src/plugin-new.ts:129-130`, `packages/develop/docs/commands/plugin.md:14`). So every registered command is a line of `bash` away from every job.

What the code says it enforces: three commands look at `ARTHUR_JOB` and refuse part or all of themselves inside a job: `arthur decision` (every verb), `arthur youtrack` (the writes), `arthur plugin new` (any folder but the job's own worktree). The CLI refuses everything inside an eval session (`ARTHUR_EVAL`). Nothing else looks at where it runs: `cli.ts:44-47` runs any command found, and `docs/deploy.md:31` states the position as it is ("a job runs `omp` with `bash` and can do whatever you can").

How each row was checked: by reading the lines named and the tests named, and by two throwaway probes (not committed), run in a temporary folder with a config of orchestration, projects, delivery and schedule, the home folder under it, and no channel, bot, VPS or client repository: (1) the real CLI (`packages/core/src/cli.ts`) with `ARTHUR_JOB` set to a record path, one state-changing command each with a bogus job id, a wrong kind or a missing file, so nothing was spawned, stopped or merged, to see whether the command refuses "inside a job" or reaches its own logic; (2) `envRefusal` and `worktreeRefusal` on `bash` calls of the form `cd ~/arthur && arthur <command> …`, with and without the variable cleared on the line. The probe's output is quoted in the rows as `probe:`.

Verdicts: `holds`, `holds without a test`, `gap` (a `findings.md` entry each), or a pointer to the area whose ticket carries it.

## AR0311's notes

- F5 (a job can run Arthur's state-changing commands: merge unreviewed, spawn without a budget, stop, send): confirmed, in every part. Probe 1: with `ARTHUR_JOB` set, `merge --unreviewed`, `merge --auto`, `spawn --budget 0 --timeout 0`, `continue --budget 0`, `stop`, `stopall`, `steer`, `prune`, `send`, `ticket new`, `ticket status … planned`, `ticket status … --autopilot`, `review`, `review-needed`, `coordinator stop`, `silent on`, `schedule add --task` each reached its own first check or acted; `decision ask` alone refused, and acted once the variable was cleared on the line.
