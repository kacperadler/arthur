## 1. limits.test.ts fails under load: three tests race a fixed 3 s job limit
Kind: test
Budget: 3
Evidence:
- `packages/core/test/limits.test.ts:143,159,211`: three tests spawn a job with `timeoutMinutes: 0.05` (3 s). Each then waits at `:144`, `:160` and `:214` for something the job writes only if it gets past the sandbox's start before those 3 s are up: the tool's pid file, the install's pid file, or the `limit: budget: stopping the agent` log line.

- I ran `node --import @arthur/core/testing --test --test-name-pattern "timeout during" packages/core/test/limits.test.ts` here with nothing else running: the tool-call test took 3230 ms against its 3000 ms limit. The margin is small even on an idle host.
- The same failure has been filed five times, always passing when the file runs alone:
  - AR0425 F1, worker 2026-10-28-worker-04c1fca5: `:144` timed out.
  - AR0494 F1, worker 2026-10-28-worker-444ea31a: `:144` and `:214` timed out.
  - AR0541 F2, worker 2026-10-29-worker-8705208f: `:160` timed out, then three tests in one run.

  - AR0552 F3, worker 2026-10-28-worker-eddb9bac: `:160` timed out. It names the cause: the job is stopped before the install writes its pid file.
Why it matters: every worker and reviewer runs the full suite while other worktrees run theirs, so these false failures keep showing up as findings and doubts in rounds that cost money. The styleguide asks for a test that "waits until the very state it asserts holds", and these three wait on a state a lost race never reaches.

Then assert the reason the job ended with in both cases, or give the tested limit a start point that does not depend on how fast the sandbox starts. The job limits and the wrapper stay as they are; no other test file is touched.
