## 1. A project agent's reply uses up the coordinator's `arthur silent ask`, so the coordinator's decision question is held and never sent
Kind: fix
Budget: 4
Evidence:
- `packages/orchestration/src/silent.ts:113`: `arthur silent ask` writes one shared `silent-ask` time into orchestration's own folder, whichever session runs it.
- `packages/orchestration/src/inbox.ts:175`: `sweep` checks each session's outbox, project agents included, against that one file (`held(host.folder, name)`). The first reply from any session written after the ask removes the file (`silent.ts:94-99`).
- I reproduced it with a throwaway `node --import @arthur/core/testing` script using `fakeHost` and `inbox()`. Setup: silent on, an ask at 1000, then shop's agent's reply to a job's end (`1500-000001.json`, `channels: []`) swept. The coordinator's question (`2000-000001.json`) was swept after it. Output: `replied: ["Shop: the job ended."]`, `coordinator held: [ '2000-000001.json' ]`, `ask left: false`. Silent mode should have held shop's job-end reply. Instead it went out, and the owner never got the decision question.
- `packages/orchestration/roles/project.md` never mentions silent mode or `arthur silent ask` (grep finds no match). So while silent is on, a project agent's decision question in a turn that holds only Arthur's messages is always held.
Why it matters: Silent mode has one rule it must keep: a decision always reaches the owner. Now that project agents exist, a busy project can quietly swallow the coordinator's merge or plan question.
Scope: Make each ask belong to the session that runs it, for example a `silent-ask` file in each session's folder, read by `sweep` for that session. Teach `project.md` to use `arthur silent ask` for a decision. Add a test where two sessions' replies race one ask. The global on/off switch and grants stay as they are.

## 2. A project agent's voice notes and `arthur send` files go through the main bot to the main chat, not to its own chat
Takes F1 of AR0706
Kind: fix
Budget: 5
Evidence:
- `packages/orchestration/src/voice-reply.ts:19,32`: the voice note is sent as `{ files: [spoken], place }`, with no bot.
- `packages/telegram/src/telegram.ts:73` and `packages/discord/src/discord.ts:91`: `channel.send` always calls `outgoing(main, …)`. For a project chat on a second Telegram bot, the voice note therefore goes to the main bot's chat with the agent's topic number. That topic is either missing there or belongs to another chat. Text replies are routed by `through(answers, instance)` and are not affected.
- `packages/orchestration/roles/project.md:32` tells the agent to show files with `arthur send <file>… --caption '<text>'`, with no `--place`. `packages/core/src/send-command.ts:26` then sends to every channel's allowed chat, which is the coordinator's main chat. `packages/orchestration/src/context.ts` never tells the agent its own place, and `arthur send` cannot name a bot.
Why it matters: Project agents are meant to talk to the owner in the project's own chat (vision decision 20). Today their files and spoken replies land in the coordinator's chat or in the wrong topic.
Scope: Let `channel.send` take an optional `instance` (the bot) in telegram and discord, and pass the reply's bot and place from `voice-reply.ts`. Make `arthur send` from a project agent's session go to that agent's chat (bot and place). Update the `channel.send` contract in `docs/commands/send.md` and each channel's doc. The retro's send and the coordinator's behavior stay as they are.

## 3. Two projects can share one chat without being refused when one names the main bot and the other leaves the bot out
Takes F2 of AR0705
Kind: fix
Evidence:
- `packages/orchestration/src/sessions.ts:36`: the duplicate check compares the raw `chat.instance`. `sessionFor` at `sessions.ts:51` routes with `chat.instance ?? main[chat.plugin]`.
- I reproduced it with a throwaway script calling `sessionList` on a `fakeHost`. Setup: shop `{ plugin: "telegram", place: "42" }`, blog `{ plugin: "telegram", instance: "first", place: "42" }`, and `channel.main` `first`. Output: `loaded: [ 'coordinator', 'agent:shop', 'agent:blog' ]`, and a message from bot `first` in 42 goes to `agent:shop`. Blog's agent never hears its chat, but its replies are still sent there.
Why it matters: The load-time refusal exists so two agents never share one place (roadmap 85 "Done means"). With this spelling the setup starts anyway, and one project's agent silently gets nothing.
Scope: Treat a missing bot as the channel's main bot (`channel.main`) when comparing chats. Do the check once the channels have answered: at start, or as the critical `arthur doctor` line that already refuses a chat whose plugin has no `channel.send`. Add a test for both orders. Routing itself stays as it is.

Kind: fix
Evidence:

Why it matters: Part of the AR0708 (roadmap 88) restart flow, the owner's steps after a project agent restarts, is documented but no agent can reach it.
Scope: Name the file in `project.md`. The agent's session already holds `ARTHUR_SESSION_FOLDER`, so the role can say `$ARTHUR_SESSION_FOLDER/after-restart.md`. Make the handoff request texts say "this session" instead of "the coordinator". Extend the `session/after-restart-plan` eval scenario, or add one, for a project agent. The coordinator's flow stays as it is.
